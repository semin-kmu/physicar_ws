# 02. 감시 / 하트비트

`system_supervisor` 가 주행 중 전 노드의 이상을 **검출**하는 절차.
검출 이후의 대응(MRM, 복구)은 `03`, System 상태 전이는 `04`.

<br>

## 1. 범위

| 포함 | 미포함 |
| --- | --- |
| heartbeat 메시지 정의 · 발행 규칙 | 이상 검출 후 대응 → `03` |
| stale 판정 (수신 중단 / 데이터 지연) | System 상태 전이 → `04` |
| 이상 등급 분류, 핵심/비핵심 노드 | 메시지 패키지 통합 정의 → `07` |
| 감시 tick 구조, Supervisor 자기 감시 | |
| 센서 고장과 노드 고장의 구분 | |

<br>

---

## 2. 설계 원칙

| 원칙 | 내용 |
| --- | --- |
| **"살아있음"이 아니라 "일하고 있음"** | 프로세스 생존·`ACTIVE` 상태는 판정 근거로 부족. `01` section 3 의 G4 와 동일한 원칙 |
| **기동 증거를 그대로 승계** | `01` section 5 의 G4 판정용 구독을 해제하지 않고 감시로 전환. 감시 전용 구독을 새로 만들지 않음 |
| **원본 센서 토픽 구독 금지** | 이미지·스캔은 Supervisor 가 받지 않음. 소비 노드가 heartbeat 로 보고 (section 6) |
| **판정은 Supervisor 단일 지점** | 노드가 스스로 "정지해야 한다"를 판단하지 않음. 예외는 컨트롤러의 Deadman (로컬 판정) |
| **오탐이 가장 흔한 실패 모드** | 정상 노드를 이상으로 오판해 재시작하는 것이 실주행 최대 위험. 임계는 보수적으로, 확정에는 연속 조건 |

<br>

## 3. 감시 대상 3종

| 종류 | 대상 | 수단 | 검출 가능한 고장 |
| --- | --- | --- | --- |
| **프로세스 생존** | 전 자식 프로세스 | `Popen.poll()` | 크래시, OOM kill |
| **노드 기능** | 자체 작성 노드 (분류 A) | `/diag/heartbeat` | 내부 루프 정지, 자체 진단 실패 |
| **데이터 신선도** | 출력 토픽 / TF | stamp 기반 stale (section 5) | hang, 출력 중단, 지연 |

- 외부 노드(분류 B/C, `map_server`, `ekf`, `localization`)는 **heartbeat 를 발행하지 않음** → 프로세스 생존 + 데이터 신선도 2종으로만 감시
- 이 3종은 **서로를 대체하지 못함**. 프로세스는 살아있는데 출력이 멈추는 hang 이 가장 흔하고, heartbeat 만으로는 데이터 지연을 못 봄

<br>

## 4. heartbeat

### 4-1. 메시지 정의

`kau_msgs/msg/Heartbeat` (통합 정의는 `07`)

```
std_msgs/Header header          # stamp = 발행 시각
string          node_id         # manifest 의 노드 이름과 동일 (01 section 2-2)
uint8           status          # OK=0 / DEGRADED=1 / FAULT=2
uint32          seq             # 단조 증가. 누락·재시작 검출
float32         loop_period_ms      # 최근 창의 평균 tick 주기
float32         loop_period_max_ms  # 최근 창의 최대 tick 주기 (지터)
InputStatus[]   inputs          # 입력 토픽별 상태
string          detail          # FAULT 사유. 로깅 전용, 판정에 미사용
```

`kau_msgs/msg/InputStatus`

```
string                   name        # 입력 토픽명
builtin_interfaces/Time  last_stamp  # 마지막으로 받은 메시지의 stamp
float32                  rate_hz     # 최근 창의 수신 주기
```

| 필드 | 없으면 못 하는 것 |
| --- | --- |
| `seq` | 재시작 검출: 노드가 죽었다 살아나도 heartbeat 는 계속 오므로 `seq` 초기화로만 구분 |
| `loop_period_max_ms` | **평균은 정상인데 최대가 튀는 상태**를 못 봄. 주기 노드의 초기 이상 징후 |
| `inputs` | 센서 고장과 노드 고장을 구분 못 함 (section 6) |
| `status` | 노드만 아는 자체 진단(신뢰도 저하 등)을 전달 못 함 |

### 4-2. 발행 규칙

| 항목 | 값 |
| --- | --- |
| 토픽 | `/diag/heartbeat` **단일 토픽**, `node_id` 로 구분 |
| 주기 | **10 Hz 고정** (전 노드 동일) |
| QoS | `best_effort`, `volatile`, depth 5 |
| 발행 시점 | **노드 자신의 주 tick 안에서**: 별도 타이머 금지 |

**단일 토픽인 이유**. Supervisor 의 구독을 1개로 유지. 노드당 토픽을 만들면 구독 10개 + 노드 추가 시 Supervisor 코드 수정

**별도 타이머 금지가 핵심**. `01` section 14-1 과 동일한 원리

| 발행 방식 | 노드의 주 루프가 멈췄을 때 |
| --- | --- |
| **주 tick 안에서 발행 (필수)** | heartbeat 도 함께 멈춤 → **stale 로 검출됨** |
| 별도 타이머로 발행 | 일은 안 하는데 **"정상"이라고 계속 보고** → 검출 불가 |

- 후자는 감시 체계 전체를 무력화하는 유일한 구멍 → 계약(section 10)에 명시
- `best_effort` 인 이유: 누락 1개로 판정하지 않음(section 5-2). 재전송은 지연만 늘림

## 5. 판정

### 5-1. stale · 시각 2종을 모두 본다

```
age = now - msg.header.stamp      # 데이터 지연
gap = now - last_recv_time        # 발행 중단
stale = (age > A) OR (gap > G)
```

| 지표 | 잡는 고장 | 이것만 보면 놓치는 것 |
| --- | --- | --- |
| `age` | 처리 지연, 오래된 데이터 재발행 | **발행 자체가 멈춘 경우**: 마지막 메시지의 age 는 계속 커지므로 실제로는 잡히나, 첫 검출이 A 만큼 늦음 |
| `gap` | 발행 중단, 노드 hang | **발행은 되는데 내용이 낡은 경우** (버퍼 재발행) |

- 둘 다 필요. `now` 와 `stamp` 는 **동일 시계**여야 함 → `use_sim_time` 일치는 사전 점검(`01` section 10)에서 이미 확인

### 5-2. 확정 조건 · 오탐 방지

| 조건 | 값 (잠정) | 목적 |
| --- | --- | --- |
| 이상 확정 | **연속 3 tick** stale | 순간 지터로 인한 오판 차단. 20 Hz tick → 확정까지 150 ms |
| 정상 복귀 | **연속 10 tick** 정상 | 깜빡임에 의한 등급 진동 방지 (히스테리시스) |

- 확정 지연 150 ms 는 **정지거리 예산에 포함**해야 함 (2.0 m/s → 30 cm)
- 이는 **검출 확정분만**임. `enable` 차단 정지 전체 지연은 확정 150 ms + Deadman 250 ms = **400 ms (80 cm)**. `04` section 6-4
- 복귀를 확정보다 엄격하게 두는 것은 `01` section 4-3 신호등 확정과 같은 패턴. **위험 방향으로는 빠르게, 안전 방향으로는 느리게**

### 5-3. 대상별 임계 (잠정)

**⚠ 대부분 미정.** 각 노드의 실제 동작 주기가 확정되지 않았으므로 임계를 숫자로 적지 않음. 실측 절차는 `08` section 4-0

| 대상 | `A` (age) | `G` (gap) | 상태 |
| --- | --- | --- | --- |
| `/diag/heartbeat` (노드별) | 300 ms | 500 ms | 발행 10 Hz **계약 19** 기준 |
| `/perception/start_permission` | **판정 불가** | 300~500 ms | `std_msgs/Bool` 에 `header` 없음 (`07` section 3-2) |
| `/state_machine/mission`, `/state_machine/speed_limit` | 250 ms | 250 ms | 자체 tick 20 Hz, Deadman 과 동일값 (`04` section 6-4) |
| TF `odom→base_link` · `map→odom` | **TBD** | **TBD** | 발행 주기 미정 |
| laser odometry 출력 | **TBD** | **TBD** | 노드 자체가 미확정 |
| `/lane/center` · `/perception/objects` | **TBD** | **TBD** | 발행 주기 미정 |
| `/path/local` | **TBD** | **TBD** | 재계획 주기 미정 |
| `/steer`, `/speed` | **TBD** | **TBD** | 발행 주기 미정 |

**산출 규칙 (실측 후 적용)**

| 대상 | 배수 | 근거 |
| --- | --- | --- |
| 일반 토픽 | 발행 주기 **× 3~5** | 순간 결손 흡수 |
| **명령 경로** (`/steer`·`/speed`·`/path/local`) | 발행 주기 **× 2~2.5** | 검출 지연이 곧 정지거리. 1주기 결손만 흡수 |

- **임계는 반드시 발행 주기보다 커야 함.** 작으면 상시 stale → 주행 시작 즉시 `FAULT`
- `01` section 6-1 의 G4 임계와 **방향이 반대** (G4 는 주기 이하, stale 은 주기 이상). 하나만 고치면 다른 쪽이 어긋남
- `/perception/start_permission` 은 `gap` 단독. 잃는 것은 "낡은 판정 재발행" 검출이며, `true` 는 latch, `false` 는 안전 방향이라 실질 위험 없음

**`/perception/objects` 는 출력 내용으로 판정할 수 없음**

- 라바콘은 6개뿐이고 트랙에 흩어져 있음 → **주행 시간의 대부분은 검출 0개가 정상**
- `object_detection` 이 신뢰도 필터링을 내부에서 완결하므로(계약 36), 발행된 것은 전부 유효
- **"0개"는 어떤 경우에도 이상 신호가 아님.** 개수·내용을 판정에 쓰지 않음 → 출력 판정은 **발행 주기 단독**

**구조적 한계. 출력만으로는 검출 성능 저하를 볼 수 없음**

| 시도 | 가능 여부 |
| --- | --- |
| 개수가 0이면 이상 | **불가**: 0이 정상 |
| 라바콘 예상 위치와 대조 | **불가**: 배치를 사전에 모름 |
| 1랩 누적 6개 미만이면 이상 | **불가**: 완주 후에야 알 수 있음 |
| LiDAR·카메라 교차 검증 | **노드 내부에서만 가능** (Supervisor 는 원본을 안 받음, section 6) |

→ **검출 성능 저하는 Supervisor 가 관측할 수 없음.** 이는 설계 미비가 아니라 정보의 한계

**따라서 `object_detection` 감시는 3층으로만 성립**

| 층 | 수단 | 잡는 것 |
| --- | --- | --- |
| 입력 | heartbeat `inputs[]` 의 카메라·LiDAR stale (계약 22) | **가장 실질적**: 검출 실패 원인의 대부분 |
| 처리 | `/perception/objects` 발행 주기 + `loop_period_max_ms` | 노드 hang, 처리 지연 |
| 자체 진단 | heartbeat `status` (계약 38) | 노드만 아는 품질 저하 |

**미검출 위험은 감시가 아니라 예산으로 막음**

- 라바콘을 늦게 잡거나 못 잡는 위험은 **감시로 해소되지 않음**
- 대응은 **이벤트 진입 지연을 정지거리 예산에 포함**하는 것 (`05`, 확정 지연 150 ms = 2 m/s 에서 30 cm)
- 즉 `object_detection` 은 **핵심 노드이지만 이상 검출 수단이 제한적**이라는 것을 전제로 속도 상한을 잡아야 함

## 6. 센서 고장과 노드 고장의 구분

**Supervisor 는 센서 원본 토픽을 구독하지 않음** (`01` section 10). 그러면 센서 고장을 어떻게 아는가.

```
각 노드가 자신의 입력 상태를 inputs[] 로 보고
   ↓
Supervisor 가 노드 간 교차 대조
   ↓
같은 센서를 쓰는 노드 2개 이상이 동시에 입력 stale 보고  →  센서 원인
1개만 보고                                              →  해당 노드 원인
```

**센서 → 소비 노드 (확정)**

| 센서 토픽 | 소비 노드 | 교차 대조 가능 |
| --- | --- | --- |
| `/scan` | `localization`(단독 입력), laser odometry → `ekf`, (`object_detection` 사용 시) | **가능** |
| `/imu` | `ekf` **단독** | **불가**: section 6 말미 |
| 카메라 | `lane_detection`, `object_detection` | **가능** |

| 관측 | 판정 | 대응 방향 (`03`) |
| --- | --- | --- |
| `object_detection` 만 카메라 입력 stale | 노드 원인 | 해당 노드 재시작 |
| `object_detection` **와** `lane_detection` 이 동시에 카메라 stale | **센서 원인** | 노드 재시작 무의미 → 즉시 MRM |
| `localization` **와** laser odometry 가 동시에 `/scan` stale | **센서 원인** | 동일 |
| `ekf` 만 `/imu` stale | 판정 불가 (단독 소비) | 재시작 1회 후 동일하면 센서 원인 |

**⚠ `/scan` 은 단일 실패점**

| 항목 | 내용 |
| --- | --- |
| 의존 | `localization`(유일한 입력) **+** laser odometry → `ekf` |
| `/scan` 상실 시 | **절대 위치와 상대 위치를 동시에 잃음** → `lane_only` 도 불성립 |
| 등급 | 즉시 **`FAULT`** (section 7-4 조합 규칙의 `localization` + `ekf`) |
| 복구 | 센서는 차량 제공 → **수단 없음**. 정지 유지 |

- 차량에 Wheel Odometry 가 없어 `/scan` 을 대체할 상대 위치원이 존재하지 않음
- `/imu` 만 남으면 이중 적분 dead-reckoning → **수 초 내 사용 불가 수준으로 드리프트**

- **이 구분이 없으면 "오탐으로 정상 노드를 재시작"** 이라는 `01` section 6-3 의 최대 실패 모드에 그대로 빠짐
- 센서는 대회 차량 제공이라 **우리가 복구할 수단이 없음** → 센서 원인으로 판정되면 재시작 시도를 건너뛰고 바로 정지
- 센서를 1개 노드만 쓰는 경우는 교차 대조 불가 → 그 노드는 **재시작 1회 시도 후에도 동일하면 센서 원인으로 간주**

## 7. 이상 등급

### 7-1. 등급 정의

| 등급 | 조건 | 성격 |
| --- | --- | --- |
| `OK` | 전 대상 정상 | - |
| `DEGRADED` | 비핵심 노드 이상, 또는 노드가 스스로 `DEGRADED` 보고 | 주행 계속 가능, 복구 시도 |
| `FAULT` | **핵심** 노드 이상, 또는 센서 원인 판정 | 즉시 정지 필요 |

### 7-2. 핵심 / 비핵심

| 노드 | 등급 | 근거 |
| --- | --- | --- |
| `ekf` (+ laser odometry) | **핵심** | `odom→base_link` 상실 = TF 체인 붕괴 = 전 노드 무효. **두 노드를 한 묶음으로 취급** |
| `localization` | **조건부** | 복구 실패 시 `lane_only` fallback → section 7-4 |
| `lane_detection` | **조건부** | fallback 존재 → section 7-4. 단독 고장은 `DEGRADED` |
| `object_detection` | **핵심** | 라바콘 미검출 = 충돌. **fallback 없음: 복구 불가 시 포기** (`03` section 3-1) |
| `local_path_planner` | **핵심** | 경로 생성 중단 = 제어 입력 상실 |
| `state_machine` | **핵심** | `/state_machine/speed_limit` stale → 컨트롤러가 자동 정지 |
| `steer_controller` | **핵심** | 명령 경로 |
| `speed_controller` | **조건부** | 복구 불가 시 `state_machine` 이 상수 속도 대행 (`03` section 4-4) |
| `global_path_planner` | **비핵심** | 기동 시 1회 생성 후 **런타임 역할 없음**. 경로는 latched 로 이미 전달됨 |
| `map_server` | **비핵심** | 맵은 latched 로 이미 전달됨. `localization` 이 로드 완료 상태 |

**랩 진행도 `s`. `global_path_planner` 가 계산한다는 가정은 폐기**

원칙: **최근접점은 아무도 남에게 발행하지 않음. 필요한 노드가 필요한 곡선 위에서 자기 주기로 구함.**

| 노드 | 대상 곡선 | 주기 | 용도 |
| --- | --- | --- | --- |
| `steer_controller` | **Local Path** | 100 Hz | 조향 오차 |
| `local_path_planner` | **Global Path** | 5 Hz | reference 구성 |
| `lane_detection` · `object_detection` | 각자 필요 시 | 자체 주기 | 자체 판정 |
| `state_machine` | **Global Path** | **20 Hz** | **랩 진행도 `s` / 도착 판정** |

- **곡선이 다르므로 중복 계산이 아님.** `state_machine` 이 100 Hz 로 못 도는 이상 컨트롤러에 공급할 수 없고, 컨트롤러의 100 Hz 결과는 Local Path 위 값이라 전역 진행도와 무관 (`05` section 4-1)

- 곡선도 목적도 다르므로 **주기를 맞출 이유가 없음.** controller 의 100 Hz 는 전역 진행도와 무관
- `global_path_planner` 는 기동 후 사실상 idle → **`s` 의 공급자로 부적합**
- `local_path_planner`(5 Hz)에서 받아 쓰는 것도 부적합. 판정 tick(20 Hz)과 **4배 어긋나 최악 200 ms = 40 cm 지연**

**`state_machine` 이 직접 구하는 근거**

| 항목 | 내용 |
| --- | --- |
| 소유권 | `s` 는 Mission 상태의 핵심 변수이자 **복구 시 보존 대상**(`03`). 남의 노드가 소유하면 그 노드 재시작마다 진행도가 흔들림 |
| 정밀도 | 2 m/s · 20 Hz → **10 cm 해상도**. 종료 트리거로 충분 (기록 계측은 대회측 소관) |
| 비용 | 전역 탐색이 아닌 **호길이 window 추적**(세그먼트 2~3개). 20 Hz × ~0.2 ms ≈ **0.4 % CPU** |
| 구현 | 검증 완료된 공용 curve 라이브러리 사용 → 중복 구현 아님 |

- window 를 잃으면(`state_machine` 재시작 등) **1회만 전역 탐색**(branch-and-bound) 후 추적 재개
- 입력은 TF `map→base_link` + latched Global Path. **둘 다 이미 존재**
- 도착 판정 상세(진행도 가드 + 출발선 선분 교차 + 방향 + 최소 경과시간)는 `05`

**대신 남는 실제 제약. late joiner**

- Global Path 는 `transient_local` latched → **발행 노드가 살아있어야 늦게 참여한 구독자가 받음**
- `global_path_planner` 가 죽은 상태에서 `local_path_planner` 를 재시작하면 **경로를 못 받아 복구 실패**
- 복구 순서 제약: `local_path_planner` 재시작 전 `global_path_planner` 생존 확인 (`03` 에서 확정)
- 이것이 `global_path_planner` 를 **주행 중에도 살려 두는 유일한 이유**

### 7-3. 등급 산출

```
등급 = max( 각 대상의 개별 등급,  조합 규칙(section 7-4)의 결과 )
```

- 다수결·가중치 없음. **안전 방향으로만 합성**
- 노드가 스스로 보고한 `status` 는 **Supervisor 판정을 올릴 수만 있고 내릴 수 없음**. 고장난 노드의 "정상" 보고를 신뢰하지 않기 위함
- `max` 단독으로는 **"각각은 견딜 만한데 겹치면 못 견디는"** 조합을 표현할 수 없음 → section 7-4

<br>

### 7-4. 축소 주행 모드 · 조건부 핵심 노드 2개

**확정: `local_path_planner` 는 상위 입력이 상실돼도 남은 입력만으로 주행을 계속.**

| 프로파일 | 진입 조건 | 사용 입력 | 좌표 | 등급 | 속도 |
| --- | --- | --- | --- | --- | --- |
| `lane_centering` | 평시 | Global Path + 차선 + 장애물 | 절대 | `OK` | 구간 상한 = **100 %** |
| **`global_only`** | `lane_detection` 정지 | Global Path + 장애물 | 절대 | `DEGRADED` | **60 %** |
| **`lane_only`** | `localization` **복구 실패** | 차선 + 장애물 | **상대** | `DEGRADED` | **40 %** |

> 속도는 **구간 상한 대비 비율로만 규정**함. 절대값은 구간 상한 하나만 두고(규정 확인 필요),
> 나머지는 비율로 유도. 상한이 바뀌어도 문서·설정 수정이 불필요

- **`lane_only` 는 이상 검출 즉시가 아니라 복구 시도가 실패한 뒤** 진입 (`03`). 그 전까지는 MRM 정지 상태
- 근거: 순회 트랙 1랩 기록 경기 → **중도 정지는 사실상 실격**. 남은 입력으로라도 완주하는 편이 나음

<br>

#### `global_only`. `lane_detection` 상실

| | 평시 | `global_only` |
| --- | --- | --- |
| 경로 기준 | Global Path + 차선 중앙 보정 | **Global Path 단독** |
| 라바콘 회피 | 유지 | **유지** |
| 이탈 허용 판단 | 차선 기준 | **Global Path 기준 횡방향 오프셋 한계** |

**성립 판정식**. 값은 실측 대입 전까지 미확정

```
잔여 여유 = 주행가능 반폭 − 차체 반폭 − 프로파일 추종오차 예산
성립 ⟺ 잔여 여유 > 0
```

| 기호 | 값 | 상태 |
| --- | --- | --- |
| 주행가능 반폭 | ? | **미확정**: 시뮬의 차선 반폭 35 cm 는 **예시값**. 이탈 허용이 반대 차선까지 열렸으므로(`06` section 6-2) 기준은 **트랙 주행가능 영역** |
| 차체 반폭 | 10 cm | **확정**: 차량 제원(차폭 200 mm) |
| 추종오차 예산 `w_lane = 0` | 16.22 cm | **시뮬 실측 참고치** (`src/README.md`) |
| 추종오차 예산 `w_lane = 1.0` | 2.06 cm | 동일 |

- **시뮬의 차선폭·장애물 크기로 성립 여부를 결론짓지 않음.** 판정식만 확정, 수치는 실측 후 (`08` section 11 항목 7·11)
- 값과 무관하게 성립하는 관계 하나: `global_only` 의 추종오차가 평시의 **약 8배**(16.22 / 2.06) → **어떤 실측값이 와도 `global_only` 가 먼저 여유를 소진**
- 차선 보정이 사라지면 추종 정확도가 **localization 정확도에 전적으로 의존** → 아래 조합 규칙이 필수
- fallback 주행은 **속도를 낮춘 상태**로만 허용 (section 12 에서 확정)

<br>

#### `lane_only`. `localization` 복구 실패

**절대좌표를 버리고 상대좌표로만 주행.** 잃는 것이 크므로 마지막 수단.

| | `lane_only` |
| --- | --- |
| 경로 기준 | 차선 중앙 (`base_link` 상대) |
| Global Path | **사용 안 함**: `map→odom` 이 없어 정합 불가 |
| 라바콘 회피 | 유지: **장애물 좌표가 `base_link` 상대이므로 `map` 없이 성립** (계약 35) |
| 필요 TF | **`odom→base_link` 는 여전히 필수** |

**`ekf` 는 이 모드에서도 핵심**. `lane_only` 라고 TF 가 전부 불필요한 것이 아님

- `local_path_planner` 5 Hz, `steer_controller` 100 Hz → 경로 생성 시점과 추종 시점 사이의 **차량 이동 보상**에 `odom→base_link` 필요
- `ekf` 는 laser odometry + `/imu` 융합이며 **`map` 프레임에 의존하지 않음** → `localization`(소프트웨어) 사망과 무관하게 생존
- 단 **`/scan` 자체가 죽으면 `localization` 과 `ekf` 가 함께 사망** (section 6) → `lane_only` 는 **`localization` 노드 고장에만 성립**하고 센서 고장에는 성립하지 않음
- 이것이 `01` section 9-3 의 "`localization` + `ekf` 동일 프로세스 금지"가 실제로 값을 하는 지점

**도착 판정을 하지 않음. 확정**

| 항목 | 확정 |
| --- | --- |
| 문제 | `map→base_link` 가 없어 **랩 진행도 `s` 산출 불가** (section 7-2) |
| 결정 | **도착 판정을 시도하지 않는다.** 추정 진행도도 만들지 않음 |
| 동작 | `s` 를 진입 시점 값에서 **동결**하고 **지속 주행**. 자동 정지·자동 종료 없음 |
| 종료 | **운영자 개입**: 도착 시 진행자가 차량을 들어올리거나 프로세스를 종료 |
| 근거 | 드리프트가 있는 추정 진행도로 종료를 판정하면 **트랙 한복판에서 오종료**할 수 있다. 판정하지 않는 편이 안전 |

- `lane_only` 는 **"멈추지 않는 모드"**. 완주 여부를 스스로 판단하지 않음
- **주행 시간 상한 없음** (의도된 결정). 잔여 위험은 section 12
- `localization` 복구 시 `s` 를 절대 기준으로 되돌리고 `lane_centering` 복귀 → **이때 도착 판정이 되살아남**

<br>

#### 조합 규칙. 남는 입력이 없으면 `FAULT`

| 조합 | 등급 | 근거 |
| --- | --- | --- |
| `lane_detection` 단독 | `DEGRADED` | `global_only` 성립 |
| `localization` 단독 (복구 실패) | `DEGRADED` | `lane_only` 성립 |
| `lane_detection` **+** `localization` | **`FAULT`** | 두 모드 모두 불성립: **남는 입력 없음** |
| `lane_detection` **+** `object_detection` | **`FAULT`** | `global_only` 의 두 입력이 모두 없음 |
| `localization` **+** `object_detection` | **`FAULT`** | `lane_only` 에서 장애물 회피 불가 |
| `localization` **+** `ekf` | **`FAULT`** | `lane_only` 도 `odom→base_link` 를 요구. **`/scan` 상실 시 자동으로 이 조합** (section 6) |
| `lane_detection` **+** `global_path_planner` | `DEGRADED` 유지 | 경로는 이미 수신 완료. 단 **두 노드 모두 재시작 불가 상태**가 되므로 복구 순서 주의 |

> **프로파일은 등급과 같은 노드가 낸다.** 프로파일은 `grade` 와 필수 입력 집합에서 유도되고, `grade` 판정은 Supervisor 단독(section 2)임.
> 다른 노드가 발행하면 **같은 판정이 두 곳에서 재계산**되어 desync 가 생김. `state_machine` 은 구독해서 `speed_limit` 비율에 쓸 뿐.

- 규칙의 형태는 하나뿐: **"어떤 프로파일도 입력 집합을 채우지 못하면 `FAULT`"**
- 조합을 코드에 나열하지 말 것. **프로파일별 필수 입력 집합을 데이터로 두고** 매 tick 평가

<br>

#### 전환 · 복귀

| 항목 | 규칙 |
| --- | --- |
| `global_only` 전환 | 등급 확정(연속 3 tick) 즉시 |
| `lane_only` 전환 | **복구 시도 실패 확정 후** (`03`). 검출 즉시가 아님 |
| 발행 주체 | **`system_supervisor`**: `/state_machine/profile` (20 Hz, 감시 tick 내) |
| 복귀 | 등급 복귀(연속 10 tick) 후 `local_path_planner` 가 **가중치를 램프로 복원** |
| 급복귀 금지 | 계단 복원은 경로 급변 → 조향 스텝 입력 |
| `lane_only` 복귀 | **경로 기준이 상대→절대로 통째로 바뀜** → 램프 구간을 `global_only` 보다 길게 |

**주행 중 복구 허용. `03` 의 예외 후보**

- `03` 의 원칙은 "복구 전 반드시 MRM 정지". 그 근거는 **해당 노드 출력 없이 주행하면 위험하기 때문**
- fallback 이 성립한다는 것은 그 전제가 깨진다는 뜻 → **fallback 이 검증된 노드는 정지 없이 재시작 허용**이 논리적으로 일관
- 단 조건: 프로파일 전환 완료 **AND** 속도 하향 적용 후. 확정은 `03`

**반드시 인지할 위험. 평시에 실행되지 않는 경로**

- `global_only` 프로파일은 **정상 주행에서 한 번도 실행되지 않음** → 실주행 첫 진입 시 버그가 드러나면 그 순간이 고장 상황
- 대응: 정기적으로 `global_only` **단독 주행 테스트**를 수행하고, 회귀 시나리오에 고정 (section 11)

## 8. 감시 tick

### 8-1. 구조 · 20 Hz 단일 tick

```
tick (20 Hz):
  1. 프로세스 생존 확인        poll(): 전 자식
  2. heartbeat 표 판정         age / gap (콜백은 수신만, 판정은 tick 에서)
  3. 토픽 · TF stale 판정      G4 승계 구독
  4. 교차 대조                 센서 원인 여부 (section 6)
  5. 등급 산출                 max 합성
  6. enable 발행               ← 등급이 정지 지시가 아닐 때만
  7. 상태 발행 + 전이 로깅
```

- **6번이 tick 끝에 있는 것이 핵심**. 1~5 중 어디서든 멈추면 enable 이 발행되지 않아 차량이 선다 (`01` section 14-1 대응 A)
- 콜백은 **수신·기록만** 하고 판정하지 않음. 판정이 콜백에 흩어지면 tick 정지를 검출할 수 없음

### 8-2. Supervisor 자기 감시

감시자를 감시하는 주체는 없음. 3중으로만 커버됨.

| 실패 | 커버 |
| --- | --- |
| Supervisor 프로세스 사망 | enable 중단 → Deadman → 정지. 자식은 `PR_SET_PDEATHSIG` 로 동반 종료 |
| tick 전체 정지 | enable 이 tick 안에 있으므로 함께 중단 → 정지 |
| tick 은 도는데 지연 누적 | `tick_duration > 100 ms`(주기 50 ms 의 2배)가 연속 3회 → **`/state_machine/enable` 발행 스킵** = 자기 자신에 대한 stale 판정 |

- 마지막 항목까지 넣어야 "느려진 Supervisor 가 늦은 판정으로 주행을 허용하는" 상태를 막음
- tick 실행 시간은 **항상 측정하고 로깅**. 실주행 후 임계 확정의 유일한 근거

| 24 | 자체 진단 실패 시 `status = FAULT` + `detail` 기재. **정상으로 위장 금지** | 노드만 아는 고장 전달 |
| 25 | `ACTIVE` 상태에서만 발행 (`INACTIVE` 발행 금지, `01` 계약 3과 동일) | 기동 판정 오염 방지 |
| 26 | `local_path_planner`: **`global_only` 프로파일 구현**: Global Path + `object_detection` 만으로 경로 생성 | `lane_detection` fallback (section 7-4) |
| 27 | `local_path_planner`: 프로파일 복귀 시 lane 가중치를 **램프로 복원** | 계단 복원은 조향 스텝 입력 |
| 28 | `local_path_planner`: `global_only` 에서 이탈 허용을 **Global Path 기준 횡방향 오프셋 한계**로 판단 | 차선 기준이 없음 |
| 29 | `local_path_planner`: **`lane_only` 프로파일 구현**: 차선 + 장애물만으로 `base_link` 상대 경로 생성 | `localization` 복구 실패 (section 7-4) |
| 30 | `local_path_planner`: `lane_only` 에서도 `odom→base_link` 로 **생성~추종 사이 이동 보상** | 5 Hz 경로를 100 Hz 로 추종 |
| 31 | 3개 프로파일의 **필수 입력 집합을 설정 데이터로 노출** | Supervisor 가 조합 규칙을 데이터로 평가 (section 7-4) |
| 32 | `global_path_planner`: Global Path 를 **`transient_local` latched** 로 발행하고, 기동 후에도 **프로세스 생존 유지** | late joiner 복구 (section 7-2) |
| 33 | **최근접점을 남에게 발행하지 않음**: 각 노드가 자기 곡선 위에서 자기 주기로 계산 | 주기 불일치가 판정 지연으로 전이되는 것을 차단 |
| 34 | `state_machine`: TF `map→base_link` 구독 + 공용 curve 라이브러리로 `s` 자체 산출 | 랩 진행도 소유권 (section 7-2) |
| 35 | `object_detection`: 장애물 좌표를 **`base_link` 상대좌표**로 발행. 절대좌표 변환은 소비 노드가 수행 | `lane_only` 에서 `map` 프레임이 없음 (section 7-4) |
| 36 | `object_detection`: **신뢰도 필터링을 노드 내부에서 완결.** 발행된 것은 전부 유효한 검출 | 하위 노드가 신뢰도를 재판정하지 않음 |
| 37 | `object_detection`: **`index` 를 프레임 간 일관되게 유지** (동일 물체 = 동일 id) | 이벤트 확정·해제를 id 지속성으로 판정 |
| 38 | `object_detection`: 자체 진단 결과를 **heartbeat `status`** 로 보고. 판정 근거는 **입력 품질**이며 검출 개수가 아님 | 출력으로는 성능 저하를 볼 수 없음 (section 5-3) |
