# 08. 설정 스키마

`01`~`06`·`09` 에 흩어진 모든 설정값·파라미터를 파일 3개로 통합.

<br>

## 1. 범위

| 포함 | 미포함 |
| --- | --- |
| 설정 파일 구성(개수·소유자·근거) | 판정 로직 자체 → `01`~`06` |
| 전체 YAML 스키마 | 메시지 타입 확정 → `07` |
| 파라미터 인벤토리 (전 문서 수치 집계) | 실측값 확정 자체 → 각 문서 section 확정필요 |
| 파생값 유도 규칙 (중복 정의 금지) | |
| ROS 파라미터 vs YAML 파일 구분 | |
| 기동 전 설정 검증 항목 | |
| 값 변경 시 영향 범위 | |

- 실제 YAML 파일은 만들지 않음. 전부 본 문서 코드블록으로만 존재
- 노드 목록·실행 파일명은 `01` section 2-2 확정을 그대로 참조. 본 문서는 **값의 위치**만 정의

<br>

## 2. 설정 파일 구성

### 2-1. 3개로 확정 · `monitor.yaml` 후보는 폐기

| 후보(당초 4개) | 판단 | 근거 |
| --- | --- | --- |
| `bringup.yaml` | **유지, 확장** | `01` section 8 초안을 정식화 |
| `monitor.yaml` | **폐기 → `bringup.yaml` 로 흡수** | `02` section 5-3 임계(age/gap)가 감시하는 대상은 `01` section 8 evidence 가 이미 정의한 **동일 토픽/TF**. 기동 판정용 구독을 감시로 **승계**한다는 `01` section 7-2·`02` section 2 원칙과 정합: 같은 대상을 두 파일에 따로 적으면 노드 추가 시 두 곳을 고쳐야 함 |
| `recovery.yaml` | **유지** | 복구는 "몇 번 재시도할지·얼마나 기다릴지"의 **정책**이지 "무엇을 관찰할지"가 아님: 축이 다름. 튜닝 빈도도 다르다(감시 임계는 센서 특성, 복구 한도는 대회 운영 판단) |
| `mission_profile.yaml` | **유지** | 소유 노드가 다름(`state_machine` 단독). Supervisor 는 내용을 해석하지 않고 경로만 안다 |

**결과: `bringup.yaml` / `recovery.yaml` / `mission_profile.yaml` 3개**

### 2-2. 파일별 소유·로딩

| 파일 | 소유 노드 | 읽는 시점 | 전달 방식 |
| --- | --- | --- | --- |
| `bringup.yaml` | `system_supervisor` | 프로세스 시작 시 1회 파싱, 이후 상시 참조(기동+감시+게이트) | Supervisor 내부 사용. 각 노드에는 `params`/`param_file` 필드만 발췌해 `-p`/`--params-file` 로 재주입 (section 6) |
| `recovery.yaml` | `system_supervisor` | 프로세스 시작 시 1회 파싱, 이후 복구 시점마다 참조 | Supervisor 내부 사용. 노드에 직접 전달하지 않음 |
| `mission_profile.yaml` | `state_machine` | `configure` 단계에서 `--params-file` 로 로드 | Supervisor 는 **경로 존재만 확인**(section 7), 내용 해석은 `state_machine` 소관 |

- `local_path_planner`/`steer_controller` 는 `mission_profile.yaml` 을 **직접 읽지 않음**. 값은 `state_machine` 이 계산해 `/state_machine/behavior` 로 전파(`06` section 5). 두 노드 자체 게인·가중치 수치 테이블은 각 파트 소유 파일이며 **08 범위 밖**
- `recovery.yaml` 의 `node_overrides` 는 `bringup.yaml` 의 노드별 `lifecycle` 값과 **정합 검증 대상**(section 7). 값을 두 번 적는 것이 아니라, 한쪽(`lifecycle`)이 다른 쪽(`soft_reset_max`)의 상한을 제약

**필드 표**

| 필드 | 타입 | 단위 | 근거 |
| --- | --- | --- | --- |
| `x-shared.*` | float | ms | YAML anchor: section 5-2 파생값, 동일 리터럴 이중 기재 금지 |
| `defaults.*_sec` | float | s | `01` section 6-1 |
| `gate.min_dwell_sec` | map | s | `04` section 8-3 |
| `monitor.tick_slow_threshold_ms` | float | ms | `02` section 8-2 = tick 주기 50 ms 의 2배. **확정** |
| `stages[].nodes[].classification` | enum A/B/C | - | `01` section 2-1. `recovery.yaml.node_overrides` 정합 검증 대상 |
| `stages[].nodes[].evidence.stale_age_ms/gap_ms` | float | ms | `02` section 5-3: 기동 evidence 와 통합 |
| `local_path_planner.params.replan_hz` | float | Hz | **확정 5.0** 상시. 이벤트 중 상향 없음 (`05` 계약 64). `L_plan_cm` 은 미확정(section 11) |
| `local_path_planner.params.local_path_length_m` | {min,max} | m | 검토 중 범위(1.5~5.0), 확정 시 단일값 |

**evidence `kind`. 5종으로 축소 · 확장 금지**

| kind | 파라미터 | 용도 |
| --- | --- | --- |
| `topic_once` | `topic`, `type`, (선택) `check` | latched 1회 수신 |
| `topic_rate` | `topic`, `min_hz`, (선택) `check` | 주기 발행 노드 |
| `tf_rate` | `parent`, `child`, `min_hz`, `max_age_ms` | TF 발행 |
| `tf_settled` | + `settle_sec`, `max_xy_cm`, `max_yaw_deg` | 정합 수렴 |
| `cov_below` | `topic`, `max_xx`, `max_yy`, `max_yaw` | pose covariance 수렴 (AMCL 채택 시) |

**폐지: `all_of` · `value_equals` · `safe_output`**

| 폐지 대상 | 대체 |
| --- | --- |
| `all_of` (중첩 배열) | evidence 를 **배열**로 두고 전부 AND. 중첩 파서가 사라짐 |
| `value_equals` / `safe_output` | `check` 필드 1개. 값은 **`{field, op, value, consecutive}`** 4-튜플 고정 |

- 노드 10개를 판정하려고 **중첩 DSL 인터프리터를 만들지 않는다**. `check` 는 평탄한 4-튜플이므로 파서가 20줄
- `stale_age_ms`/`stale_gap_ms` 는 kind 가 아니라 evidence 항목의 **부가 필드**. 기동 시엔 무시, 감시 승계 후 stale 판정에만 사용
- **새 판정이 필요하면 kind 를 늘리지 말 것.** 위 5종 + `check` 조합으로 표현되지 않으면 먼저 설계를 의심

```yaml
verify_hold_sec:                    # 03 section 9
  ekf: 2.0
  localization: 5.0
  lane_detection: 3.0
  object_detection: 2.0
  local_path_planner: 2.0
  state_machine: 2.0
  steer_controller: 2.0
  speed_controller: 2.0

node_overrides:                     # bringup.yaml classification 과 정합 필수: section 7 검증 1번

  laser_odometry: { soft_reset_max: 0 }

  lane_detection: { action: fallback_profile, target: global_only }
  localization:   { action: fallback_profile, target: lane_only }
  speed_controller: { action: actuation_takeover }
  global_path_planner: { action: continue }
  map_server: { action: continue }
  default: { action: TERMINATED }

localization_recovery:
  store_hz: 2.0
  stale_sec: 5.0                    # map→odom 저장값 유효기한, 03 section 6-4

emergency_steer:
  zero_tau_sec: null                 # 정지소요와 동일 크기: 실측 전 TBD (03 section 15)

actuation_takeover:
  publish_hz: 20.0
  # 속도 비율값은 여기 두지 않는다: mission_profile.yaml.fallback_profiles.actuation_takeover.ratio 단일 정의 (section 4)
```

**필드 표**

| 필드 | 타입 | 단위 | 근거 |
| --- | --- | --- | --- |
| `limits.*_max` | int | 회 | `03` section 11-1 |
| `verify_hold_sec` | map(node→float) | s | `03` section 9 |
| `node_overrides` | map | - | `01` section 2-1 분류 반영. `soft_reset_max:0` = 분류 C |
| `give_up_action` | map | - | `03` section 11-2 표를 데이터화. `default` 가 TERMINATED 대상 전부를 대표 |
| `localization_recovery.stale_sec` | float | s | `03` section 6-4 |

### 4-0-4. 주기 파생 규칙 · 실측값 하나로 두 임계가 결정됨

```
G4 min_hz     = 실측 주기 × 0.8          (01 section 6-1)   ← 주기보다 낮아야 함
stale age/gap = 실측 주기의 3~5배         (02 section 5-3)   ← 주기보다 높아야 함
```

| 규칙 | 위반 시 |
| --- | --- |
| `min_hz` > 실측 주기 | **정상 노드가 기동에 실패** (section 7 검증 13번) |
| `stale` < 실측 주기 | **상시 stale → 주행 시작 즉시 `FAULT`** (검증 14번) |

- 명령 경로(`/steer`·`/speed`·`/path/local`)는 3배가 아니라 **2~2.5배**로 좁게. 검출 지연이 곧 정지거리
- **두 임계는 방향이 반대**. 하나만 고치면 반드시 다른 쪽이 어긋남
- 실측 전까지 본 문서의 모든 주기 임계 리터럴은 **`TBD` 로 간주.** 아래 인벤토리의 값은 산출 예시일 뿐 확정이 아님

## 5. 파생값 규칙 · 같은 값 두 곳에 적지 않는다

| 파생값 | 규칙 | 산출 | 저장 위치 |
| --- | --- | --- | --- |
| 프로파일별 속도 | `구간 상한 × 비율` | `section_upper_limit_mps × fallback_profiles.*.ratio` | 절대값은 `mission_profile.yaml.section_upper_limit_mps` **하나만**. 나머지는 `ratio` |
| Deadman timeout | `발행주기 × 5` | 20Hz(50ms) × 5 = **250ms** | `bringup.yaml.x-shared.deadman_timeout_ms` 앵커 1곳 → 게이트·양 컨트롤러 파라미터가 참조 |
| speed_limit stale | Deadman과 동일 | 250ms | `x-shared.speed_limit_stale_ms` 앵커 |
| stale age/gap (일반) | `발행주기 × 3~5` | 노드별 실제 배수는 section 4 표 참조(예: heartbeat age×3/gap×5, TF×3/×3: **배수가 균일하지 않으므로 리터럴 값 유지**, 파생 공식은 신규 항목 추가 시에만 적용 | `bringup.yaml` evidence 의 `stale_age_ms`/`stale_gap_ms` |
| window FWD/BACK | `(1tick이동 + drop-out허용 + 코너컷여유) × 안전율` / `FWD/2` | (10+30+20)×2=120 / 60 | `mission_profile.yaml.lap_progress_window` |
| 1tick 이동거리 | `구간상한 ÷ 20Hz` | 2.0÷20=10cm | 구간상한 변경 시 자동 재계산 대상(코드), 값 자체는 미기재 |
| 이탈 허용 상한 | `drivable_half_width − vehicle_half_width − tracking_error_budget` | 수치 미정(경계=반대 차선까지, 06section 6-2 확정) | `mission_profile.yaml.constants.drivable_half_width_cm`(신규) + `fallback_profiles.*.tracking_error_budget_cm` 조합, 결과값은 어디에도 저장하지 않고 **매 tick 계산**(06 계약76·section 6-2). **기준이 차선 반폭에서 트랙 주행가능 영역 경계로 확장**: 구 계산식(35−10−예산) 폐기 |
| 정지거리 예산 합계 | `등급확정지연 + Deadman timeout` | 150+250=400ms | 문서 서술용. 구간상한 확정 전까지 절대 거리(80cm)는 잠정 |

- **원칙**: 절대 리터럴은 소스 1곳에만 존재. 다른 파일·필드는 참조(anchor) 또는 공식으로 유도
- `recovery.yaml.actuation_takeover` 에 속도 비율을 두지 않은 것이 이 규칙의 적용 사례 (section 3-2)

## 6. ROS 파라미터 vs YAML 파일

| 구분 | 방식 | 대상 | 근거 |
| --- | --- | --- | --- |
| **정적 구조/임계값** | YAML 파일 (`--params-file`) | `mission_profile.yaml`(state_machine), `ekf.yaml`, `amcl.yaml` | 재기동해도 동일 파일을 다시 읽으면 됨. 대용량 구조 데이터 |
| **정적 개별값** | `-p key:=value` (bringup.yaml `params` 딕셔너리를 매 spawn 시 변환) | `deadman_timeout_ms`, `gain_set`, `camera_device`, `L_plan_cm` 등 | `01` section 9-1 spawn 규약: 모든 spawn(최초 기동 **및** 복구 재spawn)에서 동일하게 주입 |
| **복구 시점 동적 상태** | `-p key:=value`, **Supervisor 메모리에서 매 respawn 마다 새로 계산해 주입**. 토픽 금지 | `initial_pose_*`, 합성된 `map→base_link`, 보존 대상(`s_mono`,`lap`,`x[k-1]`,`t0`,구간index,프로파일,latch,reengage횟수) | `01` section 6-3, `03` section 6-3·section 12: 토픽 주입은 구독자 준비 전 유실. 이 값들은 **파일에 없음**: bringup.yaml/mission_profile.yaml 어디에도 초기값만 있고 복구값은 Supervisor 가 런타임에 합성 |
| **런타임 전환** | 토픽 (`/state_machine/behavior`, 프로파일 전환) | `weight_set`, `lane_departure_limit_cm`, fallback 프로파일 전환 | `03` 계약43: 파라미터는 재시작용, 토픽은 무정지 전환용. 둘 다 지원 |

- Supervisor 자신도 `deadman_timeout_ms` 를 알아야 하지만 이는 ROS 파라미터가 아니라 `bringup.yaml.gate.deadman_timeout_ms`. 앵커로 컨트롤러 params 와 값만 공유(section 5)
- `mission_profile.yaml` 자체는 **재시작 시 다시 통째로 읽음**. 정적 구조이므로 상태 손실 문제 없음. 손실되는 것은 그 안에 없는 **런타임 누적값**(위 3행)뿐
