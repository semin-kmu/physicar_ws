# 10. 테스트 / 검증

`01`~`09` 에 흩어진 검증 시나리오 전체(1~137)를 하나의 실행 가능한 테스트 체계로 통합.
공백 보완 시나리오만 **130~139 블록**에서 신설하며, 계약 번호는 신설하지 않음.

<br>

## 1. 범위

| 포함 | 미포함 |
| --- | --- |
| 전체 시나리오(1~137) 색인·분류 | 시나리오 판정 로직 자체의 재정의 → 각 원문서 |
| 회귀 고정 세트 통합 | 테스트 코드 구현 |
| 스텁 노드 통합 명세 | `07` 메시지 스키마, `08` YAML 스키마 |
| 테스트 레벨(L0~L4)과 통과 기준 | |
| 실차 필요 항목 목록 | |
| 테스트 하네스 구조 제안 | |
| **커버리지 공백** | |

- 100~119 구간은 `07`·`08` 이 소유. 본 문서는 **색인만** 하고 판정 내용은 원문서를 따름
- 단위 cm/deg/m/s, 경로 토픽 `/path/global` `/path/local` `/lane/center`(`kau_msgs`), 정지 수단 `/state_machine/enable`·`/state_machine/speed_limit` 2계층, RMW `rmw_fastrtps_cpp`. 전 문서 공통 확정 그대로 전제

## 6. 실행 순서 (테스트 레벨)

| 레벨 | 범위 | 대상 노드 | 통과 기준(exit criteria) |
| --- | --- | --- | --- |
| **L0** | 스텁 단독 | 스텁 노드 1개 | section 5의 13개 파라미터 전부가 단독 프로세스에서 의도한 고장을 재현. ROS 그래프 불필요, pytest 단위테스트로 충분 |
| **L1** | 기동 시퀀스 | 전 노드 스텁 + 실제 `system_supervisor` | 시나리오 **1~17** 전부 통과. 회귀고정(5,6,9,11,14) 반복 실행에서 100% 재현 |
| **L2** | 감시·복구 | L1과 동일 그래프 | 시나리오 **18~59** 전부 통과. 오탐방지(19,20,22) 0오탐, 연쇄억제(46,47,50) 연쇄재시작 0건 |
| **L3** | 상태기계 로직 | 실제 `state_machine` + (perception/planning/control은 스텁 또는 실제 노드 중 택1, 단 실 ROS 그래프 위) | 시나리오 **60~99** 통과. 출발게이트(62~66), 오종료방지(75,77,78,83,85), fallback 조합(96,97) 회귀 재현. `05`의 76·80·82는 시뮬 오프라인 재현으로 선행 가능 |
| **L4** | 실차 | 전 파트 실제 노드, 실제 센서, RPi5 | section 7의 실측 확정 항목 해소. L1~L3 회귀고정 전세트 + 124,125,128 실차 재현. 대회 규정 확인 항목(section 7 하단) 해소 |

> **L1 이상은 `08` section 4-0 의 이름·주기 확정이 선행되어야 함.** 스텁으로 대체 가능한 것은 동작이지 이름이 아니며,
> manifest 의 노드명이 실제와 다르면 L3 이후 실차 단계에서만 드러난다

- **레벨 간 선행 관계가 핵심**. L1이 불안정한 상태로 L2를 돌리면 감시·복구 실패의 원인이 기동 로직인지 감시 로직인지 구분 불가 (`01` section 4-1의 "직렬 진행" 논리와 동일)
- L3 는 `07` 메시지 정의와 `08` 설정 스키마가 **구현되어 있어야** 전체 검증이 성립. 정의만 있고 `kau_msgs` 빌드가 안 됐으면 부분 검증만 가능

## 8. 테스트 하네스 구조 제안

**기존 `src/*/test/` 관행(`bootstrap.py`/`runner.py`/`README.md`)은 순수 Python 계산 시뮬. ROS 미기동.**
State Machine 검증은 `system_supervisor`/`state_machine` 실제 프로세스 + 실제 DDS 통신 위에서 이루어져야 하므로(G1~G4 관문, heartbeat, stale 판정이 전부 "실제 시간이 흐르는 프로세스 간 통신"에 의존) 이 패턴을 그대로 재사용할 수 없음.

```
kau_state_machine/test/
├── bootstrap.py          # sys.path 등록 (기존 패턴 유지) + ROS install 경로 등록
├── stub_node.py           # 범용 Lifecycle 스텁 (section 5 파라미터 전부 지원)
├── manifest_stub.yaml      # 01 section 8 bringup.yaml 스키마, executable만 stub_node로 교체 (L1/L2용)
├── scenario_runner.py      # launch_testing 기반: 실제 supervisor 프로세스 기동→시나리오 주입→토픽/서비스 관측 assert→정리
├── scenarios/
│   ├── scenario_001.py … scenario_017.py   # 01
│   ├── scenario_018.py … scenario_040.py   # 02
│   └── ...                                  # 번호는 section 2 색인표와 1:1
├── offline/                # 05 section 12: TF+Global Path 로그 재생만으로 검증되는 것만 분리
│   └── scenario_076.py, 080.py, 082.py 등
└── README.md               # 기존 파트 test README와 동일 형식(단위/실행법/결과표)
```

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 실행 프레임워크 | ROS2 표준 `launch_testing` 채택 제안 | 실제 노드 프로세스·DDS discovery·타이밍이 필요: 팀에 선례 없음, section 10 확인 필요 |
| L0 | pytest 단위테스트 (ROS 불요) | `stub_node.py` 자체 로직만 검증 |
| L1/L2 | `launch_testing` + `manifest_stub.yaml` | 전 노드 스텁, `system_supervisor`만 실제 |
| L3 | `launch_testing` + 실제 `state_machine`, 나머지 스텁/실제 혼합 | `05` 오프라인 재현분(76,80,82)은 `offline/`로 분리해 CI 비용 절감 |
| L4 | 본 하네스 밖: 실차 체크리스트(section 7-1)로 별도 관리 | 시뮬/스텁으로 대체 불가 |
| 결과 저장 | `output/` (기존 관행과 동일, 커밋 제외) | JSON 리포트, `09` 로그 스키마 재사용 검토 |
