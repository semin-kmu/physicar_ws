# 01. 기동 / 종료 시퀀스

`run.sh` 1회 실행으로 전 노드를 순차 기동해 `STANDBY` 까지 도달시키는 절차.
`system_supervisor` 의 `INIT` 상태 **내부 동작**을 정의.

> 전제: 모든 자체 작성 노드는 **Lifecycle Node**. 설계 배경은 `Notes/State_Machine_Study.md`.

<br>

## 1. 범위

| 포함 | 미포함 (별도 문서) |
| --- | --- |
| 프로세스 spawn 규약 | 주행 중 고장 감지 → `03` |
| Lifecycle 전이 순서 | heartbeat 규약 → `02` |
| 노드별 준비 완료 판정 | 출발 허가 **확정 조건** → `04` 계약 52 (`object_detection` 소관) |
| 타임아웃 · 재시도 · 기동 실패 처리 | 복구용 재기동 → `03` |
| **출발 게이트 구조** (section 4-3) | System 상태 전이 정의 → `04` |
| 종료(역순) 절차 | |

- 기동 실패와 주행 중 고장은 **정책이 다름**. 기동 중에는 차량이 정지 상태 → **재시도 관대**, 주행 중에는 **재시도 엄격**

## 2. 대상 노드

### 2-1. 분류 · Lifecycle 지원 여부로 취급이 갈림

| 분류 | 대상 | 기동 방법 | 준비 판정 |
| --- | --- | --- | --- |
| **A. 자체 Lifecycle** | `object_detection` `lane_detection` `global_path_planner` `local_path_planner` `state_machine` `speed_controller` `steer_controller` | spawn → configure → activate | `get_state` + 관측 증거 |
| **B. 외부 Lifecycle** | `map_server` (nav2) | 동일 | 동일 |
| **C. 외부 non-Lifecycle** | `ekf` (robot_localization), `localization` (Cartographer) | spawn 만 | **관측 증거 단독** |

- **C 분류가 존재한다는 점이 설계 제약**. 외부 패키지는 Lifecycle 을 지원하지 않으므로 `configure`/`activate` 관문이 없음
  → 준비 판정을 **전적으로 토픽/TF 관측**에 의존해야 하고, Soft Reset(`03`)도 불가하여 **바로 Hard Restart**
- C 분류를 A 로 승격하는 래퍼 노드는 **작성하지 않음**. 검증 부담 대비 이득 없음

### 2-2. 노드 목록 ⚠ **이름 전부 가정값**

**노드명·패키지명·실행파일명은 타 파트 패키지가 완성되어야 확정됨.** 아래는 현재 가정이며, 확정 절차는 `08` section 4-0.

| 0 | (센서 드라이버) | - | - | - | **대회 차량 제공 확정. 관리 대상 아님**: 단계 0 은 토픽 발행 확인만 (section 10) |

- `speed_controller` 에 **정적 속도 상한 파라미터를 두지 않음**. 상한은 `/state_machine/speed_limit` 토픽값이 유일한 원천.
  정적 파라미터를 병행하면 원천이 둘이 되고, stale 시 `0` 으로 수렴하므로 폭주 방어에도 불필요 (`08` section 5)
- 노드 목록은 **코드 상수 아님**. `bringup.yaml` (section 8) 로 관리 → **이름 확정 시 YAML 수정만으로 끝남** (`08` 계약 90)

- `node_id` 는 이 표의 이름과 **완전 일치**해야 함 (`02` 계약 20) → 노드명 확정과 heartbeat 감시가 같은 시점에 묶임
- `map_server` 필요 여부는 **확인 필요**. Cartographer localization 은 pbstream 을 직접 로드하므로, 점유격자 맵이 시각화 외 용도로 안 쓰이면 제거

## 4. 단계 구성

### 4-1. 진행 방식 · 단계별 완전 통과

```
단계 N:  spawn → G1 → G2 → configure → G3 → activate → G3 → G4 → barrier
                                                                    ↓
단계 N+1: ...
```

- 한 단계의 **모든 노드가 G4 를 통과**해야 다음 단계 진입 (barrier)
- 같은 단계 내 노드는 **병렬 처리**

**직렬 진행을 택한 이유**

| 항목 | 판단 |
| --- | --- |
| 총 기동 시간 | 잠정 30~60 s (RPi5). **신호등 GREEN 전에만 끝나면 되므로 예산 충분** |
| 실패 국소화 | 어느 단계에서 깨졌는지 즉시 특정: 병렬 기동은 원인 추적이 어려움 |
| 데이터 의존 | `local` 은 global path 수신 후 activate 해야 첫 주기부터 정상 출력 |

> 최적화 여지: 무거운 노드(`object_detection`, `lane_detection`, 카메라 open)를 **선행 spawn 만** 해두고 configure 는 순서대로 하는 방식. **1차 구현에서는 도입하지 않음** (실패 국소화 우선)

### 4-2. 단계 표

| 단계 | 노드 | 선행 조건 | 근거 |
| --- | --- | --- | --- |
| 0 | 사전 점검 (section 10) | - | 파일/디바이스 부재를 spawn 전에 검출 |
| 1 | `map_server` | - | 맵이 먼저 올라와야 localization 이 정합 시작 |
| 2 | (laser odometry), `ekf` | - | `odom→base_link` 가 있어야 Cartographer 가 TF 체인 구성 |
| 3 | `localization` | 1, 2 | `map→odom` 발행 시작 |
| 4 | `object_detection`, `lane_detection` | - | 상호 무관 → 병렬 |
| 5 | `global_path_planner` | 3 | `map→base_link` 유효해야 랩 진행도 `s` 초기화 |
| 6 | `local_path_planner` | 4, 5 | global path + 인지 입력 필요 |
| 7 | `state_machine` | 4, 5, 6 | 하위 계층 출력이 있어야 Mission 판단 |
| 8 | `steer_controller` | 7 | - |
| 9 | `speed_controller` | 8 | **구동계를 마지막에 연다** |

**`steer` → `speed` 순서**

| 순서 | 결과 |
| --- | --- |
| `speed` 먼저 | 조향 미준비 상태에서 구동 가능 → **제어 없는 직진** |
| `steer` 먼저 | 구동 불가 상태에서 조향만 준비 → **차량 이동 없음** |

- 순서는 **2차 방어**. 1차 방어는 enable 미발행 상태의 Deadman
- 단계 4, 5 의 상대 순서는 무관. 의존 관계 없음

### 4-3. 출발 게이트 · Lifecycle 이 아니라 값으로 연다

**확정: 신호등 GREEN 시점에 컨트롤러를 activate 하지 않음.**
기동 완료 시점에 **전 노드가 이미 `ACTIVE`** 이고 인지·계획·제어 파이프라인이 전부 돌고 있으며,
출발은 `속도 상한` 값이 `0` → 목표값으로 바뀌는 것만으로 이루어짐.

- Lifecycle 전이는 수백 ms~수 s 가 걸리고 실패 가능성이 있음 → **출발 트리거로 부적합**
- 기동 순서(section 4-2)는 여전히 유효. 그것은 **기동 시 안전**이고, 출발 게이트와 별개

#### 신호 경로

```
object_detection ── /perception/start_permission ──→ state_machine ── /state_machine/speed_limit ──→ speed_controller
   std_msgs/Bool, 10 Hz                                bool 소비 → DRIVING 전이        │
   GREEN 5프레임 연속 → true latch                                                      │
system_supervisor ── /state_machine/enable (Deadman) ──────────────────────────────────┴─→ steer_controller
```

#### 정지 수단은 2계층. 컨트롤러 입력은 이 2개뿐

| 채널 | 발행 | 용도 | 특성 |
| --- | --- | --- | --- |
| `/state_machine/enable` (Deadman) | `system_supervisor` | `enable` 차단 정지, 노드 사망, Supervisor 자신의 사망 | **끊김 = 정지**. 최강 수단 |
| `/state_machine/speed_limit` | `state_machine` | 신호등 대기, `speed_limit = 0` 정지, `STOP_AND_WAIT`, `FINISHED`, 구간 속도 상한 | **값 0 = 정지** |

- **두 채널 모두 "끊김 = 정지"**. `/state_machine/speed_limit` 도 Deadman 과 동일하게 **stale timeout** 을 둠.
  미수신이 T ms 를 넘으면 컨트롤러가 `limit = 0` 으로 간주 (T 는 발행 주기 20 Hz 의 5배 = 250 ms 잠정)
- **신호등 "색"을 컨트롤러로 직접 보내지 않음**. 색을 채널로 쓰면 정지 사유(장애물 정지, 감속 정지, 완주)마다 게이트 입력이 하나씩 늘고, 컨트롤러가 신호등 의미를 알아야 함
- 정지 사유가 늘어도 **채널 수는 고정**. 전부 `speed_limit = 0` 으로 표현
- 신호등 확정 판정(`GREEN` 5프레임 연속)은 **`object_detection` 담당**. `state_machine` 은 그 결과인 `bool` 만 소비 (`04` section 5-1, 계약 52)
- `/state_machine/speed_limit` 은 사유 enum 을 **로깅용으로만** 동반. 컨트롤러 로직은 값만 사용

#### 신호등 소비. 출발 사인 전용, bool 1개

**신호등은 출발선에서 1회만 쓰임. 주행 중에는 신호등이 존재하지 않음.**

**토픽 `/perception/start_permission` · `std_msgs/Bool` · 10 Hz** (`object_detection` 파트 확정, `07` section 3-2)

| 수신값 | `STANDBY` (출발 전) | `ENGAGED` (출발 후) |
| --- | --- | --- |
| `data = false` | 정지 유지 | **무시** |
| 미수신 (`gap` 초과) | 정지 유지 | **무시** |
| `data = true` | **출발** | **무시** |

- 판정은 **화이트리스트**. "불허면 정지" 가 아니라 "`true` 여야만 출발". 미검출·통신 두절의 기본값이 자동으로 정지가 됨
- **색을 받지 않음.** `GREEN` 5프레임 연속 판정과 latch 는 `object_detection` 내부 완결 (`04` section 5-1)
- `header` 가 없어 `age` 판정 불가 → **`gap` 단독** (`02` section 5-3)

**출발 후 latch. 신호등 입력 영구 무시**

| 항목 | 내용 |
| --- | --- |
| latch 시점 | `data = true` 관측 → `DRIVING` 전이 |
| latch 이후 | `/perception/start_permission` 값을 **판정에 일절 사용하지 않음** (로깅만) |
| 이유 | 주행 중 신호등이 없으므로, 이후 들어오는 모든 신호등 검출은 **정의상 오검출** |
| latch 없을 때 위험 | **`object_detection` 재시작 시** 그쪽 latch 가 풀려 `false` 재발행 → 트랙 한복판에서 정지 |

- 복구 후 재engage 시에도 **신호등을 다시 보지 않음**. 재engage 조건은 `03` 의 복구 검증 (신호등 무관)
- `object_detection` 은 latch 이후에도 발행을 **유지** (노드 헬스 판정에 사용). 신호등 검출 파이프라인 비활성화는 RPi5 부하 실측 후 판단 (section 15)

**확정 조건은 `object_detection` 소관** (`04` 계약 52). `state_machine` 은 재판정하지 않음

- **타임아웃으로 자동 출발하지 않음**. `data = true` 미수신 시 `STANDBY` 무한 유지 (신호 주기 미상)

#### 즉시 출발 규약. 상한은 EMA **뒤**에 적용

```
v_raw    = f(κ_window)              RED 대기 중에도 상시 연산
v_smooth = EMA(v_raw, τ = 0.4 s)    RED 대기 중에도 상시 갱신
출력      = min(v_smooth, limit)     ← 게이트는 맨 마지막
```

| 적용 위치 | GREEN 직후 거동 |
| --- | --- |
| **`min` 을 EMA 뒤 (채택)** | limit 이 바뀌는 즉시 `v_smooth` 출력: **지연 0** |
| `min` 을 EMA 앞 | 0 에서 τ 로 상승 → 95% 도달까지 약 1.2 s 손해 |

- RED 대기 중 `local_path` · 곡률 · EMA 가 전부 warm → GREEN 시 **차가운 시작이 없음**
- 출발선은 직선이므로 대기 중 수렴값이 곧 직선 목표속도

#### 출발 가속. State Machine 소관 아님

- `limit` 이 `0 → 2.0` 계단 변화로 전달되는 것이 **정상 동작**
- 계단 입력을 어떻게 추종할지(가속 제한, 슬립 방지)는 **`speed_controller` 내부 책임**
- State Machine 은 **상한값만 전달**하고 프로파일을 만들지 않음. 게이트와 제어를 섞지 않기 위함

#### enable 발행 시작 시점

| 시점 | 장단 |
| --- | --- |
| **`STANDBY` 진입 시 (채택)** | Deadman 경로를 기동 중 검증 가능, GREEN 직후 지연 없음 |
| `ENGAGED` 진입 시 | 첫 enable 발행까지 지연 발생, Deadman 미검증 상태로 출발 |

- `STANDBY` 에서 enable 을 발행해도 **차량은 움직이지 않음**. `speed_limit = 0` 이 유지되므로
- enable 발행 주기 20 Hz, 컨트롤러 Deadman timeout **250 ms**. 상세 근거는 `04` section 6
- 안전은 **순서가 아니라 명령값 0** 이 보장
- **전 노드 G4 통과 전에는 enable 을 절대 발행하지 않음**
- `/perception/start_permission` 미수신·`false` 시 `speed_limit` 은 **0 유지** → 검출 실패의 기본값이 정지

## 5. 노드별 준비 완료 판정 (G4)

관측 창 = 1.0 s. 주기는 창 내 수신 횟수로 산출. **모든 임계값 잠정. 실측 후 확정**

> **주기 임계는 전부 미정.** 각 노드의 실제 동작 주기가 확정되지 않았음. 확정 절차는 `08` section 4-0

| 노드 | 관측 대상 | 판정 조건 |
| --- | --- | --- |
| `map_server` | `/map` (transient_local) | 1회 수신 + `width·height > 0` |

**`localization`. 알고리즘 2종 병행 검토 중. 판정 구조는 공통, 추가 검사만 다름**

| | Cartographer (localization 모드) | AMCL (`nav2_amcl`) |
| --- | --- | --- |
| 분류 (section 2-1) | **C**: non-Lifecycle | **B**: Lifecycle |
| 맵 입력 | `.pbstream` 직접 로드 | `map_server` 의 OccupancyGrid **필수** |
| covariance 발행 | **없음** | `/amcl_pose` 에 포함 |
| 준비 판정 | `tf_settled` 단독 | `tf_settled` **+ `cov_below`** |
| 초기 pose 주입 | `initial_pose_*` 파라미터 | `set_initial_pose` 파라미터 |
| Soft Reset (`03`) | **불가**: 바로 Hard Restart | **가능**: Lifecycle 재초기화 |

- **어느 쪽이든 `tf_settled`(`map→odom` 안정) 가 주 판정**. `map→odom` 은 누적 드리프트 보정값이라 수렴하면 거의 변하지 않는 성질을 그대로 사용
- covariance 는 **가용할 때만 보조 검사**. Cartographer 는 발행하지 않으므로 필수 조건으로 둘 수 없음
- EKF covariance(`/odometry/filtered`)는 두 경우 모두 **로깅 전용**
- **AMCL 채택 시 분류 C 는 `ekf` 하나만 남아** 복구 전략이 단순해짐. 알고리즘 선정 시 이 점을 성능과 함께 고려
- 알고리즘 교체는 **manifest 항목 교체**로 끝나야 함 (section 8). Supervisor 코드에 알고리즘 이름을 넣지 말 것

**`lane_detection` 은 기동 시 예외 없음**
- 주행 중 `lane_detection` 고장에는 fallback 이 있으나(`02` section 7-4), **기동 실패에는 적용하지 않음**
- 기동 시점은 차량이 정지 상태 → **고칠 기회가 있음**. 열화된 구성으로 출발할 이유가 없음
- 즉 `lane_detection` G4 실패는 다른 노드와 동일하게 재시도 후 `INIT_FAILED`

**컨트롤러 판정이 곧 Deadman 검증**
- 단계 8, 9 시점에는 enable 이 아직 발행되지 않음
- 이 상태에서 안전값이 나오지 않으면 **Deadman 미구현/오구현** → 즉시 기동 실패 처리
- 두 컨트롤러의 deadman timeout 파라미터 **동일성도 이 시점에 확인** (다르면 반쪽 명령 위험)

> `speed_controller` 의 `0` 출력은 **enable 미발행**과 **`speed_limit = 0`** 이 동시에 성립한 결과이므로,
> 기동 판정만으로는 두 게이트를 **분리 검증할 수 없음**. 각각의 단독 동작은 section 13 스텁 시나리오 6·9 로 확인

## 6. 타임아웃 · 재시도

### 6-1. 관문별 타임아웃 (잠정)

| 관문 | 기본값 | 예외 | 근거 |
| --- | --- | --- | --- |
| G2 노드 등장 | 10 s | `localization` 20 s | Python 노드 import + DDS discovery |
| G3 configure | 15 s | `map_server` 20 s, `localization` 30 s | 맵/pbstream 로드 |
| G3 activate | 5 s | - | 무거운 초기화는 configure 에 있어야 함 (section 12) |
| G4 기능 증거 | 5 s | `localization` 30 s, `lane_detection` 10 s | 정합 수렴 / 카메라 AE 안정화 |
| 전체 기동 예산 | 120 s | - | 초과 시 `INIT_FAILED` |

#### 주기 판정 임계 규칙 · 확정 발행 주기의 0.8배

**정상 노드가 기동에 실패하는 것이 가장 흔한 자해**. 판정 임계를 확정 발행 주기보다 높게 잡으면 반드시 발생.

| 토픽 | 확정 발행 주기 | G4 임계 |
| --- | --- | --- |
| `/perception/start_permission` | **10 Hz (확정)** | **8 Hz** |
| `/diag/heartbeat` | **10 Hz (계약 19)** | **8 Hz** |
| `/state_machine/*` | **20 Hz (자체 tick)** | **20 Hz** (예외: 지터를 스스로 통제) |
| 그 외 전 토픽 | **미정** | **TBD** |

- **실측 주기가 확정되기 전에는 임계를 숫자로 적지 않는다.** 임의값을 넣으면 그 값이 그대로 구현에 들어감
- 실측 절차와 산출 규칙은 **`08` section 4-0**

- 임계 = **확정 발행 주기 × 0.8**. 동일값을 쓰지 않는 이유는 관측 창 1.0 s 안의 지터 흡수
- stale 임계(`02` section 5-3)도 같은 원리로 **발행 주기보다 커야** 함. 두 임계는 방향이 반대이므로 함께 확인할 것

### 6-2. 재시도

| 항목 | 정책 |
| --- | --- |
| 노드별 재시도 | 최대 3회 |
| 백오프 | 1 s → 2 s → 4 s |
| 재시도 단위 | **해당 노드만** kill → respawn. 같은 단계의 통과 노드는 유지 |
| 선행 단계 | 재시도해도 **되돌리지 않음** (이미 G4 통과 = 정상 동작 중) |
| 한도 초과 | `INIT_FAILED` |

**재시도 전 반드시 kill**. configure 실패 노드가 살아있으면 재spawn 시 **노드 이름 중복**으로 DDS 가 오염됨

### 6-3. 기동 실패 처리 (`INIT_FAILED`)

| 항목 | 동작 |
| --- | --- |
| enable | 발행 안 함 (애초에 미발행) |
| 자식 프로세스 | 전부 정리 (역순 종료, section 11) |
| Supervisor 프로세스 | **종료하지 않음**: 로그 보존, 상태 유지 |
| System State | `TERMINATED` |
| 로그 | 실패 노드, 실패 관문, 마지막 stderr 200줄 |

- 주행 전 실패이므로 MRM 불필요 (차량 정지 상태)
- **자동 전체 재기동은 하지 않음**. 원인 미상 상태의 반복 기동은 상황을 악화시킴. `run.sh` 재실행 허용 여부는 규정 확인 필요 (section 15)

## 7. Supervisor `INIT` 서브 FSM

```
BOOT
 └─ PREFLIGHT ── 실패 ──────────────────────────┐
     └─ STAGE_ENTER                             │
         └─ SPAWN ─── G1 ─── WAIT_NODE ─ G2 ─┐  │
                                              │  │
             ┌────────────────────────────────┘  │
             ├─ (분류 C) ──────────────┐         │
             └─ CONFIGURE ─ G3 ─ ACTIVATE ─ G3 ─┤
                                                 │
             VERIFY ─ G4 ─ STAGE_DONE            │
                │                                │
                └─ 실패 → NODE_RETRY (백오프)    │
                            └─ 한도 초과 ────────┤
                                                 ↓
    모든 단계 완료 → ALL_READY → STANDBY    INIT_FAILED
                                            (→ TERMINATED)
```

### 7-1. 의사코드

```python
def run_bringup(manifest):
    if not preflight(): return fail("PREFLIGHT")
    t0 = now()

    for stage in manifest.stages:            # 오름차순
        pending = list(stage.nodes)
        for node in pending:
            if not bring_up_node(node, t0):
                return fail(node.name)
        # barrier: 이 단계 전 노드가 G4 통과
    return ALL_READY


def bring_up_node(node, t0):
    for attempt in range(node.retry_max + 1):
        if now() - t0 > TOTAL_BUDGET: return False
        if attempt: kill(node); sleep(BACKOFF[attempt - 1])

        spawn(node)                                    # G1
        if not wait_node_appear(node, node.t_appear):  # G2
            continue

        if node.lifecycle:
            if not transition(node, CONFIGURE, INACTIVE, node.t_configure): continue   # G3
            if not transition(node, ACTIVATE,  ACTIVE,   node.t_activate):  continue   # G3

        if not verify_evidence(node, node.t_evidence): continue                        # G4
        return True
    return False


def transition(node, tr, expect, timeout):
    call_change_state(node, tr)                 # 응답 성공만으로 판단 금지
    return poll_until(lambda: get_state(node) == expect, timeout, period=0.1)


def verify_evidence(node, timeout):
    w = Window(1.0)                             # 관측 창
    return poll_until(lambda: node.evidence.satisfied(w), timeout, period=0.1)
```

### 7-2. 구현 주의

| 항목 | 내용 |
| --- | --- |
| **서비스 호출 블로킹 금지** | Supervisor 는 enable 발행을 동시에 해야 함 → 별도 콜백 그룹 + 비동기 호출, 또는 기동 전용 스레드 |
| **`poll_until` 주기** | 0.1 s 고정. 더 짧으면 DDS 부하, 길면 타임아웃 정밀도 저하 |
| **관측 창 구독 유지** | G4 판정용 구독은 기동 후에도 **해제하지 않고 감시(`02`)로 승계** |
| **상태 로깅** | 모든 관문 통과/실패에 `(node, gate, elapsed, result)` 기록: 기동 지연 분석의 유일한 근거 |

**evidence `kind` 5종. 정식 정의는 `08` section 3-1**

| kind | 파라미터 | 용도 |
| --- | --- | --- |
| `topic_once` | `topic`, `type`, (선택) `check` | latched 1회 수신 |
| `topic_rate` | `topic`, `min_hz`, (선택) `check` | 주기 발행 노드 |

## 9. 프로세스 관리 규약

### 9-1. spawn

```python
import os, signal, subprocess, ctypes

libc = ctypes.CDLL("libc.so.6", use_errno=True)
PR_SET_PDEATHSIG = 1

def _child_setup():
    os.setsid()                                  # 별도 프로세스 그룹
    libc.prctl(PR_SET_PDEATHSIG, signal.SIGKILL) # 부모 사망 시 동반 종료

argv = [exe_path, "--ros-args", "-r", f"__node:={name}"]
for k, v in params.items():
    argv += ["-p", f"{k}:={v}"]
if param_file:
    argv += ["--params-file", param_file]

proc = subprocess.Popen(
    argv,
    preexec_fn=_child_setup,
    stdout=open(f"{log_dir}/{name}.out", "ab"),
    stderr=subprocess.STDOUT,
    env=os.environ.copy(),                       # ROS_DOMAIN_ID, RMW 상속
)
```

| 규약 | 이유 |
| --- | --- |
| **`ros2 run` 금지** | 래퍼 프로세스가 생겨 SIGTERM 이 실제 노드까지 전달되지 않음 |
| 실행 경로 | `install/<pkg>/lib/<pkg>/<exe>` 직접 실행. 경로는 `ament_index` 로 조회 |
| `os.setsid()` | 종료 시 `killpg` 로 자손까지 일괄 정리 |
| `PR_SET_PDEATHSIG` | **고아 프로세스 방지**: Supervisor 사망 시 자식 생존 → 재기동 시 노드 중복.<br>단 `preexec_fn` 은 fork 안전성 문제가 있으므로 **section 14-1 (2) 의 exec 래퍼 방식으로 대체 예정** |
| stdout 리다이렉트 | 노드별 로그 분리. 크래시 원인은 stderr 에만 남음 |
| PID 파일 | `{log_dir}/{name}.pid`: 사전 점검에서 잔존 프로세스 정리에 사용 |

### 9-2. kill

```python
def kill(proc, grace=3.0):
    pgid = os.getpgid(proc.pid)
    os.killpg(pgid, signal.SIGTERM)
    if not wait(proc, grace):
        os.killpg(pgid, signal.SIGKILL)     # hang 노드는 SIGTERM 무응답
    proc.wait()
```

- **SIGKILL 에스컬레이션 필수**. 행 걸린 노드가 종료 시퀀스 전체를 막는 것이 가장 흔한 정지 실패
- `killpg` 사용. 노드가 자식(예: 이미지 디코더)을 만들었을 수 있음

### 9-3. Composition 금지 대상

| 금지 | 이유 |
| --- | --- |
| `localization` + `ekf` 동일 프로세스 | 묶으면 `map→odom` 복구 전략 무효: localization 만 재시작이 불가능해짐 |
| 독립 재시작이 필요한 모든 노드 | 복구 단위 = 노드 |

## 10. 사전 점검 (단계 0)

spawn 전에 실패를 확정할 수 있는 항목. **여기서 걸러야 원인 추적이 쉬움**

| 점검 | 실패 시 |
| --- | --- |
| 잔존 프로세스 (이전 PID 파일) | `killpg` 정리 후 진행 |
| 실행 파일 존재 (`install/.../<exe>`) | `INIT_FAILED`: 빌드 누락 |
| 필수 파일: 맵, pbstream, 파라미터 yaml, global path 제어점 | `INIT_FAILED` |
| **센서 토픽 발행**: `/scan` · `/imu` · 카메라 각 1회 수신 + stamp 신선도 | `INIT_FAILED`: 차량 측 드라이버 미기동 |
| `ROS_DOMAIN_ID` 설정 | 기본값 명시 후 진행 |
| `RMW_IMPLEMENTATION` == `rmw_fastrtps_cpp` | **`rmw_zenoh` 사용 불가 확정**: 대회 차량에 미설치. 불일치 시 강제 설정 후 진행 |
| 로그 디렉터리 쓰기 가능 · 여유 공간 | 로깅 축소 후 진행 |
| 시각 소스 (`use_sim_time` 일치) | `INIT_FAILED`: TF stamp 판정이 전부 무너짐 |

**센서는 차량 측 제공. 우리가 기동·복구하지 않음**

| 항목 | 처리 |
| --- | --- |
| 기동 | 없음. 이미 발행 중인 것을 **확인만** |
| 미발행 | `INIT_FAILED`: 복구 수단이 없으므로 재시도 무의미 |
| 주행 중 감시 | **Supervisor 가 직접 구독하지 않음** |

- **Supervisor 는 이미지·LiDAR 원본 토픽을 구독 금지**. 대역폭·복사 비용이 감시 목적에 비해 과도, RPi5 에서 그 자체가 성능 저하 요인
- 센서 신선도는 **소비 노드(`object_detection`, `lane_detection`, `ekf`, `localization`)가 heartbeat 에 실어 보고** (규약은 `02`)
- 사전 점검의 1회 확인만 Supervisor 가 직접 수행하고, 확인 후 **즉시 구독 해제**

## 11. 종료 시퀀스

### 11-1. 순서 · 기동의 정확한 역순

```
speed_controller → steer_controller → state_machine → local → global
    → lane / object → localization → ekf → map_server
```

| 단계 | 동작 |
| --- | --- |
| 1 | 정차 확인: 속도 절댓값 < 0.05 m/s 가 1.0 s 유지 |
| 2 | enable 발행 중단 → 컨트롤러가 Deadman 으로 안전값 고정 |
| 3 | 역순 `deactivate` (분류 A/B), 노드당 2 s 타임아웃 |
| 4 | 역순 `cleanup` → `shutdown` |
| 5 | 역순 SIGTERM → 3 s → SIGKILL |
| 6 | PID 파일 삭제, 로그 flush |
| 7 | Supervisor 프로세스 종료 → `run.sh` 반환 |

**`speed` → `steer` 역순인 이유**
- 감속 중 조향을 먼저 끊으면 **마지막 조향각으로 고정된 채 굴러감**
- 구동을 먼저 끊고 조향을 나중에 끊어야 정차까지 자세 유지

### 11-2. 종료는 실패해도 진행

| 상황 | 처리 |
| --- | --- |
| `deactivate` 타임아웃 | 로그 남기고 **즉시 SIGTERM 으로 진행** |
| 프로세스 SIGTERM 무응답 | 3 s 후 SIGKILL |
| 정차 미확인 | 최대 5 s 대기 후 **강행**: 명령이 끊기면 어차피 정지 |

- 기동은 "실패 시 중단", 종료는 "실패해도 강행". **반대 정책**
- 종료 절차가 blocking 되면 프로세스가 남아 다음 실행이 오염됨

### 11-3. `TERMINATED` 는 종료가 아님

| 상태 | 프로세스 |
| --- | --- |
| `SHUTDOWN` (정상 완주) | 전부 정리 후 **종료** |
| `TERMINATED` (복구 한도 초과) | 정지 유지, **종료하지 않음**: 로그 보존 |

### 13-2. 필수 시나리오

| # | 시나리오 | 기대 |

## 14. rclpy 채택 · 위험과 대응

**확정: Supervisor 는 `rclpy`.** 작업의 대부분이 프로세스 제어·서비스 호출·YAML 해석이고 실시간 제어 루프가 없음.
아래는 **rclpy 이기 때문에 생기는 위험**. 대응 불가 항목은 없으나, section 14-1 의 4건은 **구현 시 반드시 반영**해야 함.

### 14-1. 반드시 반영 (4건)

#### (1) 내부 워치독. 가장 위험한 실패 모드

- **위험**: Supervisor 프로세스는 살아있고 **enable 타이머도 계속 도는데 감시 로직만 멈춘 상태**
  (콜백 그룹 한 곳이 블로킹 / 서비스 응답 대기 / 콜백 내 예외로 루프 중단)
- **결과**: 차량은 계속 달리는데 고장 감지가 안 됨
- Supervisor **사망**은 Deadman 이 잡지만, **"반쯤 살아있음"은 아무도 못 잡음**. Deadman 의 유일한 구멍
- **대응 A (기본). 발행을 감시 tick 안에서 수행**

  ```
  20 Hz tick:  감시 평가 → 그 결과로 enable 발행       (별도 타이머 없음)
  ```

  - 감시가 멈추면 **발행도 같이 멈춤** → Deadman 이 잡음. 워치독 코드가 아예 필요 없음
  - 구조적으로 보장되므로 **실패 모드가 하나 줄어듦**. 대가는 enable 지터가 감시 부하에 종속되는 것. Deadman timeout 여유(section 14-2)로 흡수
  - 감시 작업 하나가 블로킹되면 enable 이 끊겨 차가 섬. 이는 **오탐 정지**이며, "실격이 사고보다 낫다" 원칙과 일치

- **대응 B. 타이머를 분리해야 할 경우 워치독 필수**

  ```
  감시 루프: 매 tick 마다 last_supervise_tick = monotonic()
  enable 타이머: (now - last_supervise_tick) > W  →  enable 발행 중단
  W = 감시 주기의 3배 (잠정 150 ms)
  ```

  - 지터 실측 결과 A 가 부적합할 때만 채택. 이 경우 워치독은 **선택이 아니라 필수**

- **동일 원칙을 `state_machine` 에도 적용**. `/state_machine/speed_limit` 을 별도 타이머가 아니라 **평가 tick 안에서 발행**
- C++ 이어도 같은 문제지만, **GIL 이 발생 확률을 높임**

#### (2) `preexec_fn` 과 fork 안전성

- **위험**: `preexec_fn` 은 fork 후 exec 전에 **자식에서 파이썬 코드를 실행**함. 멀티스레드 프로세스에서는 async-signal-safe 하지 않아 **드물게 데드락**
- Supervisor 는 MultiThreadedExecutor + DDS 내부 스레드 → **정확히 그 조건**
- **대응 (택 1, A 권장)**

  | | 방법 | 비고 |
  | --- | --- | --- |
  | **A** | 초소형 exec 래퍼 `kau_spawn`(C) 이 `prctl(PR_SET_PDEATHSIG)` 설정 후 `execvp` | **프로세스가 추가되지 않음**(exec 로 대체) → "`ros2 run` 금지" 규칙과 무관. 파이썬 측은 `start_new_session=True` 만 사용 |
  | B | `preexec_fn` 유지 + **spawn 전용 단일 스레드**에서만 호출 | 코드 규율에 의존, 회귀 검증이 어려움 |
  | C | `PR_SET_PDEATHSIG` 포기, 고아 정리는 PID 파일 + 사전 점검 | Supervisor 급사 시 재기동까지 고아가 남음 |

- A 채택 시 section 9-1 의 `preexec_fn` 은 `start_new_session=True` 로 대체

#### (3) 서비스 호출 블로킹

- **위험**: rclpy 동기 `call()` 을 콜백 안에서 호출하면 **같은 executor 가 응답을 처리하지 못해 영구 대기**
- Lifecycle `change_state` 는 configure 가 무거우면 수 초 소요 → 실제로 걸리는 조합
- **대응**: `call_async()` + future 폴링. 기동 로직은 **콜백이 아닌 전용 스레드**에서 실행. 모든 서비스 호출에 타임아웃 필수(section 6)

#### (4) SIGTERM 처리

- **위험**: rclpy 는 SIGINT 만 처리. `run.sh` 종료·상위 kill 은 SIGTERM
- 파이썬 시그널 핸들러는 **메인 스레드에서만** 실행되므로 spin 중이면 지연
- **대응**: 메인 스레드에서 SIGTERM 핸들러 등록 → **플래그만 세팅**, 종료 시퀀스(section 11)는 별도 스레드가 수행

### 14-2. 수용 가능 · 여유로 흡수

| 위험 | 실체 | 대응 |
| --- | --- | --- |
| enable 타이머 지터 | GIL + GC 로 수 ms~수십 ms 밀림 | Deadman timeout 을 발행 주기의 **5배 이상**. 발행은 20 Hz 감시 tick 내(`02` section 8-1)로 확정되어 **timeout = 250 ms** (`04` section 6). `gc.freeze()` + 임계 상향은 실측 후 판단 |
| 콜백 처리량 | 노드 10개 heartbeat + evidence 구독 | heartbeat 는 **단일 토픽 + `node_id`** 구조라 구독 1개. 원본 센서 토픽은 구독 금지(section 10) |
| 메모리 | 파이썬 프로세스 수십 MB | RPi5 기준 문제 없음 |
| 실시간성 | rclpy 는 실시간 보장 없음 | **Supervisor 에는 실시간 요구 루프가 없음.** 실시간이 필요한 것은 컨트롤러이며 별도 노드 |

### 14-3. 대응 못 하는 상황은 없음 · 단 결과는 확인해 둘 것

| 상황 | 결과 | 안전 여부 |
| --- | --- | --- |
| 파이썬 예외로 spin 중단 | 프로세스 종료 → enable 끊김 + 자식 동반 종료 | **안전** (정지) |
| GIL 데드락 / 무한루프 | 타이머도 멈춤 → enable 끊김 | **안전** (정지) |
| 기동 중 rclpy 예외 | INIT 미완료 → enable 미발행 | **안전** (출발 안 함) |
| **감시만 멈추고 타이머는 생존** | enable 계속 발행 | **위험** → section 14-1 (1) 워치독으로만 커버됨 |

- 결론: **안전 측면에서 rclpy 가 막아버리는 시나리오는 없음.** 잃는 것은 실시간성이며 Supervisor 는 그것을 요구하지 않음
- 얻는 것: `subprocess` · `signal` · 파일/YAML 처리가 표준 라이브러리로 끝남. Supervisor 작업의 대부분
