# kau_lane_detection

카메라 한 대로 차선을 잡아 **중앙선(황색 점선)의 quintic Bezier 제어점 6개**를
`/lane/center` 로 발행한다.

이 문서는 코드 주석에서 옮겨온 **설계 근거와 실측값**이다. 왜 그 숫자인지,
왜 그 방식인지가 여기 있다. 코드에는 "무엇을 하는지"만 짧게 남긴다.

---

## 0. 변경 이력 — 2026-08-25

이번 변경은 세 가지다. 근거는 각 절에 있다.

### 0-1. 카메라 틸트 정합 (버그) — 그리고 10도로 확정

`camera_tilt_deg` 가 yaml 10.0 / 코드 기본값 5.0 으로 갈라져 있었고,
yaml 이 이기므로 **카메라는 10도로 서 있는데 BEV 세 행은 5도 지평선을
쓰고 있었다.** 축척(`sx`, `sy`, `lane_width_px`)이 전부 그 기하에서
나오므로 발행되던 모든 cm 좌표가 같이 틀어져 있었다.

```
vanishing_y = cy - fy*tan(tilt + 0.284deg)
  5.284deg -> 180 - 261.559*0.09250 = 155.81
 10.284deg -> 180 - 261.559*0.18147 = 132.54     23.3 px 차이
```

처음에는 세 행이 이미 5도 유도값이라 **틸트를 5.0 으로** 맞췄다.
그러자 기하는 맞았지만 **경로가 거의 발행되지 않았다** — 카메라가
멀리 보게 되면서 `len` 이 190 cm 로 늘었고, 그 거리에서 도로가 휘니
`maxlat` 이 66 cm 로 나와 시야이탈 게이트(자동 한계 61.4 cm)에
걸렸다. 라이브 실측 `/lane/center` **0.66 Hz**.

그래서 반대로 갔다 — **틸트 10.0, 세 행을 10도로 다시 유도.**
멀리 보는 대신 가까이를 촘촘히 본다.

|                   | 틸트 5.0 | **틸트 10.0 (확정)** |
| ----------------- | -------- | -------------------- |
| `bev_vanishing_y` | 155.81 | **132.54** |
| `bev_src_top_y`   | 176.62 | **164.70** |
| `bev_src_bottom_y`| 270.47 | **245.24** |
| 지면 범위 | 32.2 ~ 183.7 cm | **32.4 ~ 120.0 cm** |
| `sx` / `sy` | 0.2455 / 0.3156 (비등방 0.78) | **0.2528 / 0.1826 (1.38)** |
| `lane_width_px` | 129.1 | **125.4** |

목표 지면거리 `d = 32.35 ~ 120 cm` 를 정하고
`y = cy + fy*tan(atan(h/d) - alpha)`, `alpha = 10 + 0.284deg`, `h = 14.6`
로 유도했다. **룩어헤드를 늘리는 것이 목적이 아니다** — `len` 이
70~100 cm 에 들어오면 충분하고, 대신 같은 지면이 더 많은 BEV 픽셀로
펴져 차선이 정확해진다.

라이브 실측 (정지, 직선 구간, 185 프레임 연속):

| | 틸트 5.0 | **틸트 10.0** |
| --- | --- | --- |
| `path` / `gate` | 0 / 3 (시야이탈) | **1 / 0 (185/185 통과)** |
| `/lane/center` | 0.66 Hz | **14.5 Hz** |
| `len` | 189.8 cm | **81.9 cm** |
| `maxlat` | 66.0 cm | **0.2 cm** |
| `conf` | 0.22 | **1.00** |
| `edev` | 56.3 cm | **0.1 cm** |
| 26초간 경고 | 매 프레임 재잠금 | **3건** (회랑 절단 1, EMA 이상치 1, sim 정상 1) |

`win` 44, `lw/yw/rw` 15/13/15 로 검출량도 유지된다.

### 0-2. HLS 임계 원설계값 복원

|                 | 되돌리기 전     | 현재            |
| --------------- | --------------- | --------------- |
| `yellow_hls_lo` | `[0, 80, 100]`  | `[15, 70, 150]` |
| `yellow_hls_hi` | `[20, 255, 255]`| `[35, 255, 255]`|
| `white_hls_lo`  | `[0, 205, 0]`   | `[0, 200, 20]`  |
| `white_hls_hi`  | `[180, 255, 255]`| `[180, 255, 70]`|

**노랑의 잔디 방어선이 H 에서 S 로 돌아간다.** 직전 설정은 `H <= 20`
으로 잔디(H 31~32)를 색상에서 잘랐고 S 100 은 보조였다. 복원값은
`H <= 35` 라 잔디가 색상으로는 들어오고 **`S >= 150` 이 혼자 막는다** —
§4 의 실측(잔디 S 37~91 vs 중앙선 S 225)이 이 값의 근거다.
중앙선 H 는 18 이라 15~35 안에 그대로 들어온다.

남는 위험은 하나다: **그늘에서 어두워진 중앙선의 S 가 150 아래로
떨어지면 놓친다.** 직전 설정의 S 100 이 그것을 노린 값이었다. 실차
조명에서 재확인할 것.

흰색은 `S <= 70` 이 돌아오면서 "채도가 낮다" 조건이 복구됐다. 직전에는
`L >= 205` 하나만 남아 있어서, 실차 조명에서 중앙선 L 이 205 를 넘으면
중앙선이 흰선 마스크로 새어 들어올 수 있었다 (좌/우 판정이 통째로
어긋난다).

### 0-3. 파라미터 최상위를 yaml 로 단일화

세 갈래로 깨져 있던 것을 묶었다.

**(a) `road_map.hpp` 의 constexpr 이 yaml 과 병행 존재했다.**
`lane_width_cm` 은 파라미터인데, 아래 다섯 곳은 파라미터가 아니라
`kau_road::LANE_WIDTH_CM` 을 직접 읽고 있었다 — yaml 만 고치면 축척은
따라오고 좌/우 판정·회랑·복원은 옛 값에 머무는, 경고 없는 어긋남이다.

| 자리 | 용도 |
| --- | --- |
| `identifyLine` 잔차 임계 | `0.75 * LANE_WIDTH_CM` |
| `identifyLine` 단면 기대 위치 | `LINES[i].offset_cm` |
| 흰선 하나로 중앙선 복원 | `LINES[k].offset_cm / sx` |
| 도로 밖 판정 | `roadHalfWidthCm()` |
| 좌/우 부호 판정 | `LINES[k].offset_cm < 0` |

`lineOffsetCm(i)` / `roadHalfWidthCm()` 두 멤버를 두고 전부 그쪽으로
돌렸다. 두 함수는 `LINES` 의 형태에 `lane_width_cm_ / LANE_WIDTH_CM`
비를 곱한다. 즉 **`road_map.hpp` 는 단면의 형태(선이 몇 개, 어느
순서)만 주고, 크기는 yaml 이 정한다.** 선을 추가해도 그대로 성립한다.

기동 로그도 constexpr 이 아니라 적용값을 찍는다:

```
차로 폭 31.70cm, 도로 폭 63.40cm (yaml lane_width_cm 기준)
  | 단면 -31.70cm left road edge | +0.00cm center line | +31.70cm right road edge
```

**(b) `min_pixels` / `track_step_px` 가 yaml 을 조용히 무시했다.**
생성자에서 `declare_parameter` 로 한 번 읽고 끝이라 `ros2 param set`
이 에러 없이 먹지 않았다. `refreshBevParameters()` 로 옮겨 매 프레임
재독한다. 둘 다 BEV 기하에 안 걸리므로 `changed` 검사 바깥에 둔다.
호출은 `imageCallback` 안이고 `detectLaneSlidingWindow` /
`buildCenterlinePath` 의 사용 지점보다 앞이다.

**(c) `camera_height_cm` 14.65 -> 14.6.** 14.65 는 시뮬 `model.sdf`
포즈 체인 합이지 실측이 아니었다. 실차 실측 14.6 을 우선한다. 독립적인
세 근거가 모인다:

| 근거 | 값 |
| --- | --- |
| **실차 실측** | **14.6** |
| 시뮬 model.sdf 포즈 체인 합 | 14.65 |
| 직선 프레임 역투영 역산 | 14.55 ~ 14.71 |

축척이 0.34% 움직인다 (`sx` 비례). `lane_width_px` 는 자동 추종한다.

### 0-4. 시뮬/실차 BEV 값 통일

`platform_overrides/lane_detection_real.yaml` 이 실차 주점(cy 169.603)에
맞춰 세 행을 10.4 px 내려 덮어쓰고 있었다. **그 파일을 없앴다** —
두 플랫폼을 갈라 두면 한쪽만 갱신되는 사고가 나기 때문이고, 실제로
틸트가 5/10 으로 갈렸던 것과 같은 종류의 사고다. 이제
`config/lane_detection.yaml` 하나가 유일한 출처다.

`platform:=real` 은 여전히 받는다. 해당 오버레이가 없으면 launch 가
경고만 내고 기본 yaml 로 간다 (예전에는 예외를 던지고 죽었다).
오버레이가 다시 필요해지면 `platform_overrides/lane_detection_<name>.yaml`
을 두면 그때부터 얹힌다.

> 실차 주점이 10.4 px 위라는 사실 자체는 그대로다. 실차에서 지평선이
> 어긋나 보이면 `bev_vanishing_y` 를 런타임으로 훑어 확인할 것 —
> `refreshBevParameters()` 가 매 프레임 재독한다.

### 0-5. 발행 게이트 완화

**조향 한계 게이트를 기본 끔** (`path_gate_steer_enable: false`).
최소 회전반경(18/tan20 = 49.5 cm)보다 급한 경로여도 그대로 발행한다.
"이 곡률로 돌 수 있는가" 는 하류 제어가 감속/조향으로 판단할 일이지
인지가 경로를 끊을 일이 아니다 — 급커브에서 경로가 통째로 끊기면
하류는 근거 없이 직전 값을 들고 가야 한다. 곡률은 `status` 의 `rad`
로 계속 나가므로 진단은 그대로고, 파라미터를 `true` 로 주면 예전
동작이다.

**횡방향 한계를 명시값으로** (`max_lateral_cm: 150.0`). 자동값
`0.5 * bev_out_width * sx` 는 지금 기하에서 63.2 cm 인데, 그건 BEV
캔버스 폭에서 나오는 값이라 경로가 얼마나 멀리 가는지와 무관하다.
경로가 120 cm 앞까지 가므로 R=100 cm 90도 코너의 횡변위(100 cm)가
자동값을 넘어 **정상 커브가 시야이탈로 기각된다.** 150 은 거기에
여유를 준 값이고, 게이트 본래 목적(도로 밖 물체를 문 경로를 막는 것)은
남는다.

### 0-6. BEV 유효영역 마스크

**BEV 캔버스는 사각형인데 카메라가 보는 지면은 사다리꼴이다.** 가까울수록
횡폭이 좁으므로 하단 좌우 모서리에는 원본 화소가 아예 없고,
`warpPerspective` 가 검정으로 채운다. 없앨 수 있는 영역이 아니다 —
카메라 화각의 결과다.

실측 (500×480, 틸트 10):

| 범위 | 검정 비율 |
| ---- | --------- |
| 캔버스 전체 | 10.3% |
| **히스토그램 밴드(하단 10% = 48행)** | **43.5%** |

밴드의 절반 가까이가 죽은 화소인데 그걸 모른 채 열 합산을 하고 있었다.
그리고 `INTER_CUBIC` 으로 warp 하므로 검정과 지면 색이 경계에서 2~3 px
섞이고, 그 중간색이 임계를 통과할 수 있다.

그래서 **유효영역을 명시한다.** 원본 크기의 흰 이미지를 같은 변환으로
`INTER_NEAREST` warp 해서 0/255 마스크를 만들고, 보간 띠를 없애려고
3×3 로 2회 erode 한 뒤, 형태학 정리가 **끝난 뒤** 두 마스크에 AND 한다.

- dilate **뒤에** 걸어야 한다. 먼저 걸면 dilate 가 경계 쪽으로 다시
  넓혀 새어 나온다.
- 기하가 바뀌면(`updateBevGeometry`) 다시 만든다. 원본 크기가 바뀌어도
  다시 만든다.
- 기동 로그에 유효 비율이 찍힌다 — 현재 **89.5%**.

> 참고로 이 절을 만든 계기였던 "히스토그램이 차선이 아닌 화면 엣지에서
> 높게 찍힌다" 는, 정지 프레임 실측에서는 **재현되지 않았다.** 흰 마스크
> 열 합산이 x 100~139 와 360~399 두 군데에만 잡히고 잔디·검정 영역은
> 0 이었다. 다만 밴드의 43.5% 가 죽은 화소라는 사실은 그대로이고,
> 주행 중 차선이 그쪽으로 들어가면 근거가 조용히 줄어든다. 마스크는
> 그 실패를 구조적으로 없앤다.

## 1. 대전제

- **경로는 제어점으로만 만들고 발행한다.** 이산 좌표는 만들지도 싣지도 않는다
  (`docs/경로_형식.md`). 발행 차수는 항상 5.
- **`map` 프레임으로 발행한다** (`path_frame_id: map`, 기본값). 발행 직전에
  `map <- base_link` TF 로 제어점만 옮긴다 — 내부 계산(EMA/게이트/디버그
  오버레이)은 전부 base_link 기준 그대로다 (cte/게이트 횡한계가 "자차가
  원점" 을 전제하기 때문). `s_offset = 0` 은 그대로다 (이 경로 자체의
  로컬 s 이지, `/path/global` 의 전역 s 가 아니다).
  ~~측위 비의존~~ (2026-08-24 폐기 — §8/§9 근거) — TF 조회가 실패하면
  그 프레임은 발행을 건너뛴다. `path_frame_id: base_link` 를 주면 예전처럼
  변환 없이 그대로 나가므로, 측위 없이 검증할 때는 그쪽을 쓴다.
- **차로를 고르지 않는다.** 자차가 중앙선 어느 쪽에 있든 중앙선 자체를
  추종 목표로 삼는다. 그래서 "차로 번호" 개념이 없다.

## 2. 도로 모형

맵 mesh 실측 (`custom_71e69ee938032295503bfed557fde18c.dae`,
삼각형을 x = 6.0 m 평면으로 잘라 단면을 냄. 단위 m):

| 요소            | y 범위           | 폭    |
| --------------- | ---------------- | ----- |
| road (아스팔트) | 0.8805 .. 1.5805 | 0.700 |
| ol (흰 실선)    | 0.8805 .. 0.9555 | 0.075 |
| cl (황색 점선)  | 1.2180 .. 1.2430 | 0.025 |
| il (흰 실선)    | 1.5055 .. 1.5805 | 0.075 |

- 중앙선 중심 ↔ 흰선 중심 = **31.25 cm** (차로 폭)
- 흰선 중심 ↔ 흰선 중심 = **62.50 cm** (도로 폭)

**단, 이 값은 시뮬 mesh 실측이고 현재 쓰는 값이 아니다.** 실차 트랙
실측(2026-08-25)이 확정값이다 — 흰선 안쪽 간격 56.0 + 흰선 폭 7.4 =
중심 간 **63.4 cm**, 차로 폭 **31.7 cm**.

그리고 **크기의 최상위는 yaml 의 `lane_width_cm` 이다.** `road_map.hpp`
의 `LANE_WIDTH_CM` / `ROAD_WIDTH_CM` 은 단면의 형태만 정하고, 노드는
`lineOffsetCm()` / `roadHalfWidthCm()` 에서 `lane_width_cm_ /
LANE_WIDTH_CM` 비로 환산해 쓴다 (§0-3).

**도로는 닫힌 고리다.** 같은 x = 6.0 평면이 도로를 두 번 지나고 두 통과의
선 순서가 뒤집혀 있다 (아래쪽 ol-cl-il, 위쪽 il-cl-ol). il 이 양쪽에서
안쪽을 향하므로 ol 이 바깥 경계, il 이 안쪽 경계인 무한 루프다.

그래서 "ol = 왼쪽 선" 같은 이름은 성립하지 않는다. 루프를 도는 방향에 따라
바깥 경계가 좌우 어느 쪽에도 올 수 있다. `road_map.hpp` 의 `LINES` 는 트랙
좌표가 아니라 **차량 좌표(오른쪽이 +)** 로 적는다.

영상 검증 — 직선 구간 한 프레임을 undistort 해 지면으로 역투영하면:

| 실측 대상                 | 치수    | 역산한 카메라 높이 |
| ------------------------- | ------- | ------------------ |
| 도로 바깥 가장자리 간격   | 70.0 cm | h 14.552           |
| 흰선 안쪽 가장자리 간격   | 55.0 cm | h 14.670           |
| 중앙선 ↔ 왼쪽 흰선 안쪽   | 27.5 cm | h 14.708           |
| 중앙선 ↔ 오른쪽 흰선 안쪽 | 27.5 cm | h 14.633           |

네 경로가 모두 14.6 근처로 모인다 (`camera_height_cm: 14.65`).

**다른 맵으로 옮길 때는 `road_map.hpp` 만 고치면 된다.** 판정 코드는 `LINES`
를 훑을 뿐 개수를 가정하지 않는다.

## 3. BEV 원근변환

`bev_src_top_y` 실측 (실패 프레임 77장을 undist 원본에서 다시 warp).
**아래 표는 BEV 출력이 480×360 이던 시절 값이다:**

| top_y   | 노란선 OK | Y스텝 합 | L+R OK  | LR스텝 합 | 경로 길이 | 검정 %  |
| ------- | --------- | -------- | ------- | --------- | --------- | ------- |
| 195     | 56        | 469      | 129     | 1432      | 85 cm     | 5.2     |

BEV 세로 범위가 169 → 70 cm 로 줄어드는데 경로 길이는 85 → 84 cm 로 거의
그대로다. **195 에서도 근거가 실제로 닿는 거리는 85 cm 뿐이었고 나머지는
외삽이었다는 뜻이다.**

### 출력 해상도는 look-ahead 를 되사 온다 (2026-08-25)

위 표에서 205 를 골랐던 근거 — "top_y 를 내리면 원거리 점선이 뭉개져
검출률이 떨어진다" — 는 **출력 캔버스가 480×360 으로 묶여 있던 탓**이었다.
`bev_out_width/height` 를 640×480 (가로·세로 모두 4/3배) 으로 키우면 같은
지면이 더 많은 BEV 픽셀로 펴지고, `warpPerspective` 의 `INTER_CUBIC` 보간이
원거리 마킹 가장자리 색을 덜 뭉개서 HLS 임계를 통과하는 픽셀이 늘어난다.

정차 상태 라이브 실측 (동일 자세, `len` = 발행 경로 유효길이):

| `bev_out` | `top_y` | 창 평균 | `len` 평균 |
| --------- | ------- | ------- | ---------- |
| 480×360   | 205     | 42.0    | 77.4 cm    |
| 480×360   | 195     | 40.0    | 143.3 cm   |
| **640×480** | **195** | **48.6** | **168 cm** |
| 480×360   | 188     | —       | 177.9 cm   |
| 640×480   | 188     | 46.6    | 190.5 cm   |

읽는 법 세 가지:

1. **해상도만 키우면 look-ahead 는 안 늘어난다.** `top_y` 205 를 유지한 채
   640×480 으로 가면 `len` 이 77.3 → 78.4 cm 로 제자리다 (창 개수만
   42 → 58). look-ahead 레버는 `bev_src_top_y` 하나뿐이다.
2. **그런데 `top_y` 를 내린 상태에서는 해상도가 손실을 상쇄한다.** 195 에서
   143 → 168 cm, 188 에서 178 → 191 cm.
3. **188 은 안 쓴다.** `len` 이 90~297 cm 로 요동친다 — 닿는 거리보다 외삽
   구간이 길어진다는 신호다. 195 쪽이 변동이 작다.

비용은 프레임당 **9.9 → 14.8 ms (+52%)**, %CPU 14.5 → 22.3. 드롭 0, 14.4 Hz
유지. 68 ms 예산에는 여유가 있으나 **Pi 5 는 코어당 더 느리므로 30 ms 안팎을
예상할 것.**

### 해상도를 바꿀 때 같이 손대야 하는 것

`sx = h · w_ground / dst_w` 이고 `dst_w` 는 `bev_out_width` 를 따라간다.
`sy` 는 `bev_out_height` 만 따라간다 — **가로·세로를 같은 배수로 키워야
비등방(0.76배)이 보존된다.** `lane_width_px` 는 `sx` 에서 유도되므로
자동 추종한다 (97.1 → 129.4 px).

반면 아래 셋은 **px 절대값이라 손으로 비례 조정**해야 한다. 안 올리면 창이
상대적으로 좁아진 셈이라 해상도는 키웠는데 검출률이 떨어지는 역효과가 난다:

| 파라미터         | 480×360 | 640×480 | 배수      | 런타임 변경             |
| ---------------- | ------- | ------- | --------- | ----------------------- |
| `window_margin`  | 40      | 53      | 4/3       | **가능** (매 프레임 재독) |
| `min_pixels`     | 20      | 36      | (4/3)² = 1.78 | **가능** (§0-3 에서 수정) |
| `track_step_px`  | 25.0    | 33.0    | 4/3       | **가능** (§0-3 에서 수정) |

`min_pixels` 만 제곱인 이유: 창은 진행방향 `track_step_px`, 횡으로
`2·window_margin` 이라 **면적**이 (4/3)² 로 커진다.

`track_max_steps`(48) 는 그대로 둔다 — `track_step_px` 가 4/3 배, `sx` 가
0.75배라 물리 도달거리가 보존된다 (48·33·0.75 ≈ 48·25).

`refreshBevParameters()` 가 매 프레임 다시 읽는 것은
`bev_src_center_x/top_y/bottom_y`, `bev_vanishing_y`,
`bev_src_bottom_width`, `bev_dst_margin_ratio`, `bev_out_width/height`,
`camera_height_cm`, `lane_width_cm`, `window_margin`, `min_pixels`,
`track_step_px`, `publish_roi_overlay` 다. 전부 런타임 스윕이 된다.

대신 흰선 검출은 129 → 107 로 17% 준다 (하단 모서리 검은 영역이
5.2 → 12.8% 로 커지며 연석을 먹는다). **205 를 택했다** — 노란선 스텝 +46%
를 챙기면서 흰선 손실은 -15% 에 그치고 BEV 세로 90 cm 를 남긴다.

`bev_vanishing_y: 179.0` 은 live undistort 프레임 직접 스윕으로 위/아래
간격이 일치한 값 (위 194.9 / 아래 195.4).

**축척은 파라미터가 아니다.** `lane_width_px = lane_width_cm / sx` 이고
`sx` 는 `camera_height_cm` 과 intrinsic 에서 유도한다. px 는 BEV 설정이
바뀌면 같이 변하는 내부 단위라 다른 패키지와 맞출 수 없고, 실제와 어긋나도
겉으로 드러나지 않기 때문이다.

## 4. HLS 색 임계

OpenCV `BGR2HLS` 규약: H 0~179, L/S 0~255.

**노랑 S 하한이 결정적이다.** live BEV 실측:

| 대상        | H     | L       | S     |
| ----------- | ----- | ------- | ----- |
| 잔디        | 31~32 | 118~137 | 37~91 |
| 노란 중앙선 | 18    | 110     | 225   |

S 하한 70 이면 잔디가 통과해 노랑 peak 가 중앙선(239)이 아니라 왼쪽
잔디(117)에 꽂히고, 흰선 밴드까지 어긋난다. **150 이면 잔디(≤91)와
중앙선(225)이 깨끗하게 갈린다.**

**현재 월드 BEV 실측으로 재검증했다 (2026-08-25).** 되돌린 값이 맞다:

| 대상 | H | L | S | 현재 임계 |
| ---- | - | - | - | --------- |
| 주황 중앙선 | 18 | 117 | 255 (5%ile 157) | **100% 통과** |
| 흰선 | 25 | 232 | 32 | 통과 |
| 잔디 | 33 | 117 | 90 | **0% (오검출 없음)** |

위 §4 표(H 18 / L 110 / S 225)와 거의 그대로 맞는다. 잔디 H 33 이
노랑 상한 35 안에 들어오지만 S 90 이 하한 150 에 막힌다 — **S 가
방어선**이라는 원설계가 실측으로 확인된다.

현재 값 (§0-2 에서 이 설계로 복원):

| | lo `[H,L,S]` | hi `[H,L,S]` |
| --- | --- | --- |
| yellow | `[15, 70, 150]` | `[35, 255, 255]` |
| white | `[0, 200, 20]` | `[180, 255, 70]` |

흰색의 `S <= 70` 이 "채도가 낮다" 조건이고, 이것이 중앙선을 흰선
마스크에서 빼는 유일한 근거다. 풀면 `L >= 200` 하나만 남아 밝은
조명에서 중앙선이 흰선으로 새어 들어온다.

형태학 정리(OPEN → CLOSE → dilate)는 `yellow_mask` / `white_mask` 에 직접
건다. 슬라이딩 윈도우가 그 두 마스크를 쓰기 때문이다.

**edge 근거가 없다.** 파이프라인은 `cvtColor(BGR2HLS)` → `inRange` ×2 →
형태학이 전부이고, Sobel/Canny 계열은 한 곳도 없다. 그래서 색만 맞으면
잔디·연석·정지선·반사가 마스크를 통과하고, §5 의 기하 게이트들
(`lane_side_min_ratio` / 회랑 / `center_outlier_ratio`)이 **잡고 나서
버리는** 역할을 떠맡고 있다. 마스크 단계에서 gradient 를 AND 로 걸면
면(面)으로 밝은 것과 선(線)으로 밝은 것이 갈리는데, 아직 미구현이다
(§12).

## 5. 방향성 슬라이딩 윈도우

창이 y 격자에 묶여 위로만 올라가면 차선이 가로로 누운 구간에서는 원리상
이어질 수 없다. 창을 진행 방향으로 회전시켜 차선을 따라 돌아간다.

실패 프레임 73장 실측 (노란선 주성분 방향): 가로에 가까움(<45°) 59장,
<20° 18장, y 밴드 3개 이하에 갇힘 33장.

### track_step_px — 코너 추종을 지배하는 값

한 스텝에서 흡수 가능한 방향 변화가 대략 `atan(margin/step)` 이다.
step 40 → 45° / 25 → 58° / 20 → 63°.

| 40     | 40장          | 65/77     | 7.1 px     | 12.9     | 20.4     |

| 20     | 59장          | 77/77     | 10.8 px    | 17.4     | 31.9     |

### 히스토그램 밴드

곡선에서 BEV 차선은 기울어져 있어서, 밴드가 세로로 길면 그 안에서 차선이
옆으로 쓸려 peak 가 뭉개진다. 실패 70장 실측 (peak 오차):

| 밴드     | 중앙  | 90%ile | 최대   | 다른 차선을 잡음 |

비면 2배 → 4배로 넓혀 재시도한다 (점선 공백 대비).

### 흰선 좌/우 검증 — lane_side_min_ratio

흰선 base 는 x 구간 히스토그램으로 찾는데, 차선이 세로로 서 있을 때만
"x 로 왼쪽" = "차로의 왼쪽" 이다. 90° 코너에서 차선이 가로로 누우면 좌/우
흰선이 노란선의 위/아래에 쌓여 x 구간이 반대쪽 선을 물어 온다.

추적 후 노란선 기준으로 재보고 반대쪽이면 버린다. 실패 프레임(노란선 추적
성공 55장) 실측:

|               | L엉뚱 | R엉뚱 | 같은선 | L성공  | R성공  |
| ------------- | ----- | ----- | ------ | ------ | ------ |
| 검증 없음     | 11    | 5     | 8      | 40     | 48     |
| **부호 검증** | **0** | **0** | **0**  | **29** | **43** |

### 흰선 회랑 — lane_corridor_lo / hi

흰 마스크에는 차선만 있지 않다. 체커보드 연석, 정지선, 급커브에서 보이는
트랙 다른 구간의 차선까지 들어오고 방향성 창은 구분하지 못한 채 갈아탄다.
차로 폭은 고정이므로 노란선에서 그만큼 떨어져 있지 않은 점은 우리 차로의
흰선이 아니다. **이탈한 지점에서 자른다** (통째로 버리지 않는다).

실패 프레임 63장 실측: 흰선 검출 L34/R53 중 이탈 L7/R3. 추적점 1309개 중
68개(5%)만 절단, 3점 미만이 된 건 2건. 그 프레임들에서 중심선이 최대
117 cm 달라졌다.

### 중심선 후보 이탈 — center_outlier_ratio

세 차선이 각각 중심선 후보를 하나씩 내놓는다. 하나가 엉뚱한 선을 물면

| 제거 기준      | 중앙       | 90%ile      | 최대        |
| -------------- | ---------- | ----------- | ----------- |
| 제거 없음      | 10.4 px    | 77.1 px     | 105.5 px    |
| **0.30W 이상** | **7.1 px** | **12.9 px** | **20.4 px** |
| 0.50W 이상     | 8.5 px     | 16.0 px     | 32.3 px     |

## 6. 경로 표현 — 왜 호길이 매개변수인가

`x = f(y)` 형태는 차선이 가로로 누우면 `dx/dy = ∞` 라 표현 자체가
불가능하다. **90° 코너가 통째로 끊기던 원인이었다.** 호길이 `s` 로
매개화하면 방향 전제가 사라진다.

90° 코너는 s 에 대한 사분원이라 2차로는 모자라고 3차면 충분하다. 3차
매개곡선은 t 에 대해서도 정확히 3차이므로 멱기저 → Bernstein → degree
elevation 이 전부 정확한 기저 변환이다. **근사가 한 번도 개입하지 않는다.**

`confidence = clamp(source_windows / 30, 0, 1) × cover_ratio`.
근거량 30 은 실측 중앙값 29개에서 왔다 (직선 구간에서 포화).

## 7. 시간축 강건화 (EMA)

발행 게이트는 프레임 하나만 보고 통과/기각을 정한다. **임계값을 조이면
멀쩡한 차선이 떨어져 나가고, 풀면 도로 밖 노란 물체(원경의 그림 등)가
통과한다.** 어느 쪽이든 하류 state machine 의 fail-safe 판정이 흔들린다.
프레임 하나로는 못 정하는 문제라 시간축을 쓴다.

1. 게이트를 통과한 관측을 EMA 추정치에 섞되, **섞는 양(alpha)을 그 프레임의
   confidence 에 비례**시킨다. 믿기 힘든 프레임은 추정치를 조금밖에 못 움직인다.
2. 추정치에서 `path_ema_gate_cm` 이상 벗어난 관측은 **아예 안 섞고, 직전
   추정치를 그대로 내보내면서 confidence 만 떨어뜨린다.** 하류는 "경로는
   계속 오는데 신뢰도가 미끄러진다" 를 보고 스스로 판단할 수 있다.
3. 같은 주장이 `path_ema_relock_frames`(3) 번 연속 오면 노이즈가 아니라 실제
   변화로 보고 **재잠금**한다 (없으면 진짜 차선 변화에 영원히 눈감는다).

### 게이트는 dt 에 비례해 넓힌다

두 안전장치의 **단위가 서로 달랐다.**

| | 형태 | dt 에 따라 |
| --------------------------- | ------------- | ---------- |
| `path_max_step_cm_per_s` | 속도 80 cm/s | `80·dt` — 자동 조정 |
| `path_ema_gate_cm` (예전) | 절대 15 cm | **고정** |

14 Hz 에서 15 cm/프레임은 210 cm/s 에 해당한다. 4 Hz 로 떨어지면 같은
15 cm 가 60 cm/s 가 되어 **3.5배 더 조여진다.** 그러면 프레임이 느려질수록
멀쩡한 관측이 전부 이상치로 걷어차이고 추정치가 얼어붙는다. 얼어붙은
추정치는 base_link 기준 고정이라 차가 움직여도 제자리에 머물러, 화면에서는
**"경로가 천천히 원래 자리로 돌아오는"** 것으로 보인다.

실측 (부하로 프레임이 느려진 구간의 로그 60건):

| 관측-추정치 편차 | 중앙 | 최대 | 당시 상한 |
| ---------------- | -------- | -------- | --------- |
| | 30.4 cm | 76.8 cm | **15.0 cm** |

재잠금이 105 회 걸렸다.

그래서 게이트도 dt 로 비례시킨다:

```
gate = path_ema_gate_cm × clamp(dt / (1/14), 1, path_ema_gate_dt_scale_max)
```

공칭 14 Hz 에서는 설정값 그대로라 **기존 동작이 보존된다.** 느려진 만큼만
넓어지고, 배율 상한(6)이 파이프라인 정지 시 게이트가 통째로 무력화되는
것을 막는다. 실제로 적용된 값은 `status` 의 `egate` 로 나간다 — `edev` 와
나란히 봐야 기각 여부가 설명된다.

**자기운동 보정은 아직 없다.** §1 의 측위 의존 전환으로 map <- base_link
TF(`lookupVehiclePose()`)는 이제 있지만, EMA 는 여전히 base_link 상대
좌표만 섞는다. 차선을 따라가는 동안 base_link 기준 경로는 거의 불변이라
편향이 작지만, 속도가 붙으면 추정치가 뒤로 끌리는 지연이 생긴다 — TF 로
프레임 사이 자차 이동만큼 EMA 추정치를 미리 밀어주면 고칠 수 있다
(§12 미해결).

EMA 로 섞은 제어점은 관측 당시의 진단값과 짝이 맞지 않으므로
길이/곡률/cte/heading 을 다시 재고 `valid_length` 도 따로 EMA 한다.
`valid_length` 는 하류가 LookAhead 를 자르는 근거라 특히 그대로 두면 안 된다.

튜닝은 `status` 의 `edev` (관측-추정치 편차)를 보고 잡는다. 정지 상태
직선 구간 실측이 0.2 cm 였다.

## 8. Pan 기반 Lane Lost Recovery

한쪽 흰선이 연속으로 안 잡히면 카메라를 그쪽으로 돌려 찾는다.

### BEV 가정이 깨진다 — 그런데 회전만 보정하면 된다

`updateBevGeometry()` 의 src 사다리꼴은 "카메라가 정면을 본다"를 가정한
고정값이라, 픽셀 ↔ BEV 대응(호모그래피) 자체는 카메라가 돌아가도 안
바뀐다. `bevScale()` 의 row→전방거리 / column→횡거리 유도도 intrinsic 과
소실점 행(`bev_vanishing_y`)만 쓰므로 **순수 요(yaw) 회전에는 불변이다**
— yaw 는 지평선이 찍히는 행을 옮기지 않는다.

즉 `buildCenterlinePath()` 가 내는 좌표는 처음부터 "지금 카메라가 보는
방향" 기준의 X전방/Y좌 였을 뿐이다. 거기에 실측 pan 각
(`actual_pan_deg_`, `/joint_states` 미수신 시 마지막 명령각)만큼 pan
피벗을 중심으로 회전만 더하면 base_link 기준이 된다 (6-b 절). Bezier 는
아핀변환(회전+평행이동)에 닫혀 있으므로 제어점만 옮기면 곡선 전체가
옮겨진다 — 다시 적합할 필요가 없다. pan 피벗 위치는
`pan_pivot_offset_x_cm` / `_y_cm` (기본 0,0 — 카메라 마운트 재실측
전까지는 base_link 원점과 같다고 둔다. pan=0 에서는 이 값이 얼마든
영향이 없다).

그래서 tf2 로 매 프레임 사다리꼴 자체를 다시 세우는 "진짜" 동적 BEV
(픽셀 재추출)는 필요 없었다 — **매 프레임 경로를 짓고, 그 경로를 pan
각만큼 계속 회전시키는 것으로 충분하다.**

> 2026-08-24 이전에는 이 사실을 놓쳐 `Idle` 이 아닌 동안 경로를 통째로
> 건너뛰었다. 그 결과 탐색+Holding+복귀 한 사이클(짧으면 수 초, 길면
> `pan_hold_timeout_s` 상한 없이 무한) 동안 `/lane/center` 가 끊겨,
> 하류에서 "경로가 생겼다 말았다" 하는 것으로 보였다. 이제는 pan
> 중에도 매 프레임 경로가 나간다 — `pathGate()` 의 시야이탈 판정과
> `drawPathOverlay()` 도 같은 회전을 반영(또는 역회전)해 판정/그리기
> 한다.

**기본 켜짐이다** (`pan_search_enable: true`, launch 인자 `pan_search`).
다만 `pan_hold_timeout_s` 가 0(무한 대기)이면 직선 구간을 만날 때까지
`Holding` 이 계속되므로 **경로가 낡는 시간에 상한이 없다.** 주행 중 그게
곤란하면 `pan_hold_timeout_s` 에 값을 주거나 `pan_search:=false` 로 끈다.

### 회전 부호

URDF `physicar.urdf.xacro` 와 시뮬 `model.sdf` 모두 `camera_pan_joint`
axis = **+Z** 이므로 `+rad = 왼쪽(반시계)`, 한계 ±0.5236 rad (±30°).
따라서 왼쪽 흰선을 놓쳤으면 +, 오른쪽이면 - 로 돌려야 소실된 쪽을 본다.

> 예전에는 부호가 반대였다. 실기에서 놓친 쪽의 **반대편**으로 고개를 돌리는
> 것을 확인하고 고쳤다. `pan_sign` 은 이것과 무관한 하드웨어 배선용
> 뒤집개이므로 그쪽으로 덮지 말 것.

### 인터페이스 (physicar_driver_node / model.sdf 대조 완료)

|                 | 내용                                                         |
| --------------- | ------------------------------------------------------------ |
| `/camera/pan`   | `std_msgs/Float64`, 절대각 [rad]                             |
| 실기            | `apply_pan()` 이 ±30° 로 클램프. **단 `camera_engaged()` 면 무시** (teleop/웹UI가 카메라를 잡고 있을 때) |
| 시뮬            | `JointPositionController` (p=15, d=0.1)                      |
| `/joint_states` | `camera_pan_joint` position [rad], 50 Hz                     |
| 실기            | **서보 인코더가 없어 마지막 명령각을 그대로 되쏜다** → settle 판정이 항상 즉시 참 |
| 시뮬            | Gazebo 실측 관절각 (진짜 피드백)                             |

### 각속도 램프 — 그리고 예전에 실패했던 이유

목표 각도와 발행 각도를 분리해, 발행각이 `pan_rate_deg_s`(기본 30 deg/s)
로 목표를 향해 매 프레임 조금씩 다가간다. 상태기계는 목표만 정하고
(`commandPan`), 발행은 `publishPanRamped` 가 한다.

> 한때 이 방식을 썼다가 실기에서 "꺾다 말다" 하는 움직임이 나와 스텝
> 방식으로 되돌린 적이 있다. **원인은 램프가 아니라 정착 대기가 없었던
> 것이다** — 서보가 쫓아가는 도중의 영상으로 재검출 판정을 반복했다.
> 지금은 두 가지가 그 실패 모드를 막는다:
>
> 1. `settled = (램프가 목표 도달) && (서보가 명령 도달)`
> 2. 재검출 기준이 `found_count > 0` 에서 **창 6개 × 2프레임**으로 상승

**실기에서 오히려 이쪽이 정직하다.** 서보 인코더가 없어 `/joint_states`
가 명령의 에코라 서보 정착 판정은 **항상 참**이다. 즉 스텝 방식의 실기
동작은 정착 대기가 사실상 없어서, 스텝이 프레임마다 나가고 서보는 끝까지
쫓기지 못한 채 명령각만 앞서 갔다. 램프의 "목표 도달" 판정은 우리가
발행하는 값이라 인코더 없이도 정직하게 여러 프레임이 걸린다.

### 회전 각도는 영상 시각의 값을 쓴다

경로를 base_link 로 되돌릴 때 쓰는 각도는 **영상이 찍힌 시각**의
pan 각이어야 한다. 예전에는 `actual_pan_deg_` 를 그냥 읽었는데,
그건 스탬프 매칭 없이 50 Hz 콜백이 덮어쓰는 스칼라라 **처리 시각**
의 값이다. 카메라가 도는 중이면 그 사이 각도가 바뀌어 있으므로,
길이 L 경로의 먼 끝이 `L·Δθ` 만큼 밀린다:

| Δθ | L=77 cm 끝단 오차 |
| ------ | ----------------- |
| 3°     | 4.0 cm            |
| 8°     | 10.7 cm           |
| 15°    | 19.9 cm           |

지금은 두 겹으로 막는다.

1. **스탬프 보간** — `jointStateCallback` 이 `(스탬프, 각도)` 를
   `pan_history_` 에 1 초분 쌓고, `panAngleAt(영상 스탬프)` 가 앞뒤
   두 샘플을 선형보간한다. 50 Hz 샘플 간격 20 ms 에 램프 30 deg/s
   면 그 구간 변화가 0.6° 라 보간 오차는 무시할 수준이다. 범위 밖
   이면 **외삽하지 않고** 끝값으로 자른다 (서보 거동을 모르는데
   외삽하면 없는 정보를 지어내는 것이다).
2. **각속도 램프** — 목표각을 한 프레임에 발행하면 서보는 매번 최대
   슬루로 달려 Δθ 에 상한이 없다. 각속도를 묶으면 남은 오차(보간
   구간 안쪽, 그리고 실기의 서보 추종 지연)의 상한도 같이 묶인다.

소요 시간: 0→15° 0.50 s, 한 스텝 3° 0.10 s, 0→30° 전량 1.00 s.
복귀는 계단이 아니라 목표를 0 으로 한 번 세우고 램프로 돌아온다.

> `actual_pan_deg_` 는 남아 있지만 이제 **서보 정착 판정 전용**이다
> ("서보가 지금 명령에 도달했는가"). 경로 회전에 쓰면 안 된다.
>
> 실기 주의: 서보 인코더가 없어 이력에 쌓이는 값은 실측이 아니라
> 명령의 에코다. 그래도 **명령 자체가 램프로 시간에 따라 변하므로**
> 영상 시각의 명령각이 처리 시각의 명령각보다 정확하다. 남는 오차는
> 서보 추종 지연이고 인코더 없이는 관측 불가다.

진단은 status 의 `pdfix`(적용된 보정량 [deg])와 `pdext`(스탬프가
이력 범위 밖이라 끝값으로 잘렸는가)로 본다. `pdfix` 가 0 근처면 그
프레임에서는 카메라가 사실상 정지해 있었다는 뜻이다.

### 복귀 조건 — "직선" 이 아니라 "보이는가"

예전에는 도로가 펴지면(추적점의 꺾임각) 복귀했다. **"도로가 곧다" 와
"정면으로 돌아가도 그 선이 보인다" 는 다른 명제다.**

실측: 정지 상태의 곧은 구간에서 왼쪽 흰선이 화면 밖에 있었다. 도로는 곧으니
직선 판정은 통과하고, 복귀하면 여전히 안 보이니 즉시 재탐색이 걸렸다.
**15초에 9번 왕복**했고 그동안 `/lane/center` 가 계속 끊겼다. 직선 임계값을
아무리 조여도 멎지 않는 종류의 문제다.

그래서 목적을 직접 잰다. BEV → 원본 영상 역호모그래피로 추적점의 영상각
`a = atan((u − cx) / fx)` 을 복원하면, pan 각 θ 에서 본 그 점은 pan = 0 일 때
영상각 `a − θ` 에 온다. 이것이 화면 반각 안에 드는 점이
`pan_return_min_points` 개 이상이면 복귀해도 다시 잡는다.

> 역호모그래피는 원본 영상과 BEV 사이의 **순수 2D 사상**이라 pan 으로 깨진
> 평면 가정과 무관하게 정확하다. 깨지는 것은 BEV 좌표의 "미터 해석" 이지
> 픽셀 대응이 아니다.

실제 카메라: `fx = 201.4, cx = 240` → **수평 FOV 100°**, 반각 50°.
FOV 가 넓어 pan 15° 정도에서는 대부분의 점이 정면에서도 보인다고 나온다.
왕복이 남으면 `pan_return_fov_margin_deg` 를 10~15 로 올려 조인다.

### 짧은 점열로는 판정하지 않는다

`trackBendDeg` 는 4점이면 각을 낸다. 4점 = 3스텝 × 25 px ≈ **24 cm** 이고,
그 길이로는 어떤 코너도 직선으로 보인다. `track_step_px 25`,
`sx 0.322 cm/px` 기준 절반 비교값:

| 점수   | 구간      | R=100 cm      | R=150 cm      | R=250 cm     |
| ------ | --------- | ------------- | ------------- | ------------ |
| 4      | 24 cm     | 6.9 통과      | 4.6 통과      | 2.8 통과     |
| 6      | 40 cm     | 11.5 기각     | 7.7 통과      | 4.6 통과     |
| 8      | 56 cm     | 16.1 기각     | 10.8 기각     | 6.5 통과     |
| **10** | **72 cm** | **20.8 기각** | **13.8 기각** | **8.3 기각** |
| 12     | 89 cm     | 25.4 기각     | 16.9 기각     | 10.1 기각    |

정상 검출 시 추적점은 12~15개 나온다. 근거가 모자라면 "직선이 아니다" 가
아니라 **"판정 불가"** 로 다뤄 카운트를 끊는다.

## 8-b. Pan 조준 (feedforward) — 기본 경로

**§8 의 탐색 상태기계를 대체한다.** `pan_aim_enable: true` (기본)이면
상태기계는 돌지 않고 `Idle` 로 눌려 있는다. §8/§9 는 fallback 으로만
남는다 (근거가 없을 때).

### 왜 바꿨나

| | §8 탐색 | 조준 |
| --- | --- | --- |
| 판정 | 소실 래치 (3프레임 연속 miss) | 매 프레임 연속량 |
| 명령 | 3도씩 훑는 이산 스텝 | 방위각 그대로 |
| 발진 | **있다** (§8 실측 15초 9회 왕복) | 래치가 없어 구조적으로 없다 |
| 지연 | 3프레임 소실 감지 + 램프 + 정착 + 3도 스텝 | 없음 |

탐색은 "놓친 뒤에 찾는" 방식이라 커브가 끝날 무렵 도착한다. 조준은
도로가 휜 만큼 미리 돌린다.

> 발진의 원인은 "검출을 근거로 삼는 것" 자체가 아니라 **소실 래치**였다.
> §8 은 "안 보임 → 돌린다 → 보임 → 복귀 → 안 보임" 을 상태로 왕복했다.
> 조준은 같은 검출을 쓰더라도 래치 없이 매 프레임 각을 다시 내므로
> 그 모드가 없다. 아래 `lane` 근거가 성립하는 이유가 이것이다.

### 조준 근거 — `pan_aim_source`

| | `lane` (기본) | `global` |
| --- | --- | --- |
| 근거 | 이 노드가 방금 만든 `LanePath.ctrl` | `/path/global` + 측위 |
| 측위 | 필요 없음 | AMCL 필요 (Cartographer 금지) |
| 앞먹임 | 보이는 데까지만 | 안 보이는 커브도 안다 |
| 권장 gain | **0.7** (아래) | 1.0 |

`lane` 이 성립하는 근거는 **`path.ctrl` 이 이미 base_link 기준**이라는
것이다 — `buildCenterlinePath` 가 `camera_yaw_deg` 만큼 pan 피벗 중심으로
제어점을 회전시켜 둔다 (§8 "회전 각도는 영상 시각의 값을 쓴다"). 거기서
잰 방위각은 카메라 기준이 아니라 **차체 기준 절대각**이라, 카메라를 10도
돌려도 차선이 그대로면 다음 프레임 값이 같다. 각이 적분되지 않는다.

> BEV 픽셀에서 잰 값(`trackBendDeg` 등)을 그대로 조준각으로 쓰면 안 되는
> 이유가 여기 있다. 그쪽은 카메라 좌표계라 pan 할수록 값이 다시 커져
> 발산한다. §9 처럼 **불리언 트리거**로는 되지만 연속 제어에는 못 쓴다.
> (덤으로 `trackBendDeg` 는 `std::abs` 라 부호가 없다.)

**가림 대응은 `valid_length_cm` 이 전부다.** 그 값은 근거 점이 끊기기 전
까지의 호길이이고 그 뒤는 외삽이므로, 가림이 생기면 저절로 줄어든다.
조준 거리를 그 값으로 자르면 "가려지지 않은 데까지만 보고 조준한다" 가
클램프 한 줄이 된다. 별도의 가림 검출을 두지 않는다.

### ★ `lane` 은 완전히 열린 고리가 아니다 — gain 을 1 미만으로

회전 보정에 쓰는 각도가 **실기에서는 서보 인코더가 없어 명령의 에코**다.
서보 추종 지연 `δ = θ_cmd − θ_act` 만큼 경로가 과회전되고, 그것이 방위각에
그대로 더해져 다음 명령을 키운다:

```
카메라가 실제로 본 각    ψ − θ_act
+θ_cmd 만큼 회전 보정 →  ψ + (θ_cmd − θ_act) = ψ + δ
```

DC 루프게인이 1이면 이 오차가 안 죽는다. 그래서 `lane` 소스의
`pan_aim_gain` 은 **0.7** 이다. `global` 은 고리 자체가 없어 1.0 이
안전했다 — **소스를 바꿀 때 gain 도 같이 봐야 한다.**

### 계산

`global`:

1. `/path/global` 전 구간에서 자차 최근접점 (`nearestOnSeg`)
2. 거기서 **호길이로** `pan_aim_lookahead_m` 전진
3. 그 점의 base_link 기준 **방위각**
4. `pan_aim_gain` 배

`lane` (`panAimGoalDegFromLane`):

1. `valid_length_cm >= pan_aim_min_evidence_cm` 인지 확인 (아니면 무효)
2. 조준 거리 `d = min(pan_aim_lookahead_m·100 − x_base_cm, valid_length_cm)`
   — `x_base_cm` 을 빼는 것은 경로가 카메라 앞 약 32 cm 에서 시작하므로
   `global` 과 룩어헤드의 뜻을 맞추기 위함이다
3. 호길이 `d` 인 `u` 를 이분탐색 → `evalSeg` → `atan2(y, x)`
   (원점이 자차라 뺄 것이 없다)
4. `pan_aim_gain` 배

공통 후처리 (`updatePanSearch`):

5. `min(pan_max_deg, atan(cx/fx) − pan_aim_fov_margin_deg)` 로 클램프
6. 직전 **목표각**과 `pan_aim_deadband_deg` 이상 차이날 때만 목표 갱신
7. `commandPan` → `publishPanRamped` (±`pan_max_deg`, `pan_rate_deg_s`)

### 근거가 빈 프레임 — 홀드, 0 복귀 금지

조준이 무효인 프레임에서 **정면(0)으로 되돌리면 안 된다.** "안 보임 →
정면 복귀 → 보임 → 다시 조준" 이 §8 실측 왕복(15초 9회)의 형태 그대로다.
`pan_aim_hold_frames`(14 ≈ 1초) 장까지는 직전 목표각을 유지하고, 그것을
넘기면 조준을 포기하고 §8 탐색 상태기계로 넘긴다 — 차선이 통째로 사라진
상황은 "찾아 도는" 쪽이 맡는 게 맞다.

status 의 `pahold` 가 그 연속 장수다. 0 이 아닌 값이 오래 이어지면 근거가
계속 모자란다는 뜻이므로 `pan_aim_min_evidence_cm` 을 먼저 본다.

### 호출 위치 — 경로를 짓고 **나서** 돈다

`updatePanSearch` 는 16-c-2 가 아니라 **16-d-3**, 즉 `robustifyPath`(EMA)
뒤에 있다. `lane` 근거가 이 프레임의 경로이기 때문이다. 직전 프레임 경로를
쓰면 14 Hz 에서 70 ms 지연이고, v_max 요구 각속도 143 deg/s 기준 10° 라
못 쓴다.

- 16-c-2 와 16-d-3 사이에는 조기 반환이 없다 → pan 이 갱신되지 않는
  프레임은 생기지 않는다
- `buildCenterlinePath` 가 쓰는 `camera_yaw_deg` 는 `panAngleAt()` 에서
  따로 나오므로 여기서 pan 을 갱신해도 순환이 생기지 않는다
- EMA 를 거친 경로를 쓰므로 조준 신호가 이미 저역통과돼 있다 (§8 탐색에는
  없던 감쇠다)

호길이는 정확히 잰다 — 구간 전체는 `seg_length`(사전계산), 마지막 부분
구간만 `segLength()` 이분탐색. §9 의 `curvatureAheadKappa` 가 쓰는 u 균일
근사를 재사용하면 안 된다 (그쪽 주석: *"트리거 판정용이지 제어에 쓰지
않는다"*).

원호 위에서 조준각은 이렇게 갈린다:

```
psi = d/(2R)  +  atan(e/d)
      곡률분     횡오차분
```

**구현부 로직을 원(quintic 근사) 위에서 그대로 돌려 검증한 값** (d = 1 m):

| R [m] | e=0 | e=10 cm | e=20 cm |
| ----- | ------- | ------- | ------- |
| 1.0 | **28.65** | 33.63 | 38.10 (30 포화) |
| 1.5 | **19.10** | 24.42 | 29.33 |
| 2.5 | **11.46** | 16.98 | 22.20 |
| 5.0 | **5.73** | 11.36 | 16.79 |

e=0 열은 `d/(2R)` 와 **0.005° 이내로 일치**한다. 포화점이 R = 0.955 m 라
`curve_ahead_kappa_thresh 0.01`(= R 100 cm)이 가리키는 트랙 최급커브와
±30° 한계가 거의 맞는다.

### 횡오차분을 왜 남겨 뒀나

접선 방위를 쓰면 횡오차에 불변이지만, **그건 원하는 게 아니다** — 차가
실제로 20 cm 밀려 있으면 차선도 그만큼 밀려 보이므로 카메라가 따라가야
한다. 방위각은 그 둘을 합쳐서 낸다.

아래는 **`pan_aim_source: global` 일 때만** 해당한다. `lane` 은 측위를
아예 안 쓰므로 이 표와 경고가 통째로 사라진다 — 그게 `lane` 의 가장 큰
이점이다.

측위 잡음이 `e` 에 섞여 들어오는 건 맞다. 다만 크기가 무시할 수준이다
(`kau_localization/README.md` 정지 실측):

| 측위 | `map->odom` 지터 | d=1 m 환산 |
| --- | --- | --- |
| **AMCL** | 1.12 cm / 0.094° | **0.64°** |
| Cartographer | 4.88 cm / 1.39° | 2.79° |

> ⚠️ **Cartographer 와 같이 쓰지 말 것.** 변화율 최대 167 cm/s 라 허위
> 각속도가 96 deg/s 까지 나온다. 커브 진입에 필요한 신호가 143 deg/s
> (v_max) 이라 **대역이 겹쳐 EMA 로도 못 가른다.** 필터 문제가 아니라
> 측위 선택 문제다. README 도 다른 이유(차를 들어 옮기는 복구)로 AMCL 을
> 권한다.
>
> ⚠️ 위 수치는 **정지 지터**다. README 가 *"주행/회전 중 정확도는 측정하지
> 않았다"* 고 명시한다. 튜닝 전에 주행 중 측위 정확도부터 잴 것.

### 되돌리기

`pan_aim_*` 은 `bev_*` 파라미터와 같은 idiom으로 **매 프레임 다시 읽는다**.
`pan_search_enable`(생성자 1회)과 달리 주행 중에도 먹는다.

```sh
ros2 param set /kau_lane_detection_node pan_aim_enable false   # 즉시 §8 로 복귀
ros2 param set /kau_lane_detection_node pan_aim_source global  # 예전 조준으로
ros2 param set /kau_lane_detection_node pan_aim_gain 1.0       # global 이면 같이

ros2 launch kau_lane_detection lane_detection.launch.py pan_aim:=false
ros2 launch kau_lane_detection lane_detection.launch.py pan_aim_source:=global
```

실차에서 주행 중 A/B 가 되므로 두 근거를 같은 구간에서 비교할 수 있다.
비교할 때 `pan_aim_gain` 을 같이 옮기는 것을 잊지 말 것.

§8 상태기계 코드는 **한 줄도 지우지 않았다.** `updatePanSearch` 최상단의
조기분기 하나만 추가했고, 거기서 반환하지 않으면 예전 동작 그대로다.

`pan_search_enable: false` 가 우선한다 (카메라를 아예 안 움직임).

### 미해결 — 조준을 켜기 전에

- **`pan_rate_deg_s: 30` 이 부족하다.** 상시 추종에 필요한 각속도는
  `gain·d·(dkappa/ds)·v` 다. R=1 m 진입(완화 0.5 m) 기준 v=0.6 m/s 에
  34 deg/s, **v_max 2.5 m/s 에 143 deg/s**. 30 으로는 28.6° 도달에 0.95 s
  가 걸리고 그동안 2.4 m 를 간다 — 커브가 끝난 뒤 도착한다.
  올리면 프레임당 Δθ 가 커져 §8 회전 보정 오차가 같이 커지고,
  `path_ema_gate_cm: 15.0` 에 걸려 경로가 기각될 수 있다. 같이 봐야 한다.
- **`pan_pivot_offset_*` 이 (0,0) 초안값이다** (§12). pan≠0 이 예외가
  아니라 상시 상태가 되므로, URDF 실측 (5,0) cm 와의 오차가 30° 에서
  횡 2.5 cm 계통편차로 **상시** 실린다. 차로폭 31.25 cm 의 8% 다.
  **조준을 켜기 전에 재실측할 것.**
- **§12 의 "pan 사이클 미검증" 이 더 중요해진다.** 램프와 각도 시각
  보정이 한 번도 실제로 안 돌아봤는데, 이제 그게 주 경로다.
  `pan_aim_source: lane` 에서는 그 보정 오차가 **자기 조준 입력으로
  되먹여지므로** (위 gain 절) 더 중요해진다.
- **`lane` 근거의 파라미터 넷이 전부 실측 전 초안값이다.**
  `pan_aim_gain 0.7` / `pan_aim_min_evidence_cm 25` /
  `pan_aim_deadband_deg 2` / `pan_aim_hold_frames 14`. 실차에서
  `pan_aim_source` 를 `global` 과 번갈아 두고 같은 구간을 비교할 것.
  볼 값은 status 의 `paim`(목표각) · `pahold`(홀드 연속 장수) ·
  `len`(경로 유효길이) 이다.

## 9. Pan 트리거 판정 — 곡률 룩어헤드 + 장애물 (map 프레임)

> §8-b 조준이 켜져 있으면(기본) 이 절은 **동작하지 않는다.** 조준이
> 불가할 때만 fallback 으로 쓰인다 — `pan_aim_source: lane` 이면 차선
> 근거가 `pan_aim_hold_frames` 를 넘겨 모자랄 때, `global` 이면 측위나
> `/path/global` 이 없을 때다.


차선이 화면에서 사라지는 이유는 두 가지다.

1. 코너를 돌면서 시야 밖으로 나갔다 → **고개를 돌리면 보인다**
2. 앞의 장애물에 가렸다 → **돌려도 안 보인다** (가린 물체가 따라온다)

2번에서 탐색을 걸면 상한까지 헛돌고 그동안 경로만 끊긴다. 영상만으로는
구분할 수 없다.

> 2026-08-24: `/scan_filtered` 직접 스캔 방식(부채꼴 + 각도 의존 상한)을
> 걷어내고 map 프레임 정보 두 가지로 바꿨다. §1 의 측위 의존 전환과
> 세트다.

### 왜 이제 /perception/obstacles 를 쓰는가

예전 판단(map 프레임이라 TF 필요, Gazebo 참값 pose 의존)은 낡았다.
`laser_scan_clusterer_node.cpp` 를 다시 보면:

- 장애물을 map 프레임에 앉히는 건 `/model/physicar/pose` 가 아니라
  **`tf_buffer_->lookupTransform("map", scan.header.frame_id, scan_stamp)`**
  — 진짜 TF2 조회다.
- Gazebo `world_pose`(`/model/physicar/pose`) 는 **진단 전용 사이드채널**
  로 격하돼 있다. 코드 주석: *"Nothing in this package transforms
  perception output with it"*. 실제 발행 여부를 정하는
  `decide_object_list_status_from_placement()` 는 **scan 유효성 + tf2
  변환 성공**만 본다.

즉 `map ← lidar_link`(경유 `base_link`) TF 만 서 있으면 — Cartographer 든
AMCL 이든 — **실기에서도 그대로 쓴다.**

### 곡률 우선, 그리고 가려지지 않은 쪽으로만 잰다

곡률 판정과 장애물 판정이 엇갈리면(급커브 구간인데 그 안에 장애물 원도
잡힘) **곡률을 우선한다.** 트랙 경계벽이 장애물로 오검출됐을 가능성이
더 크기 때문이다. `obstacle_lane_lateral_m`(차로 폭 이내인지)로 벽을 한
번 더 거르지만, 급커브에서는 그 여유도 좁아지므로 곡률 판정을 먼저
믿는다.

곡률 자체도 **가려진 쪽(놓친 흰선)이 아니라 가려지지 않은 쪽으로만**
잰다. 애초에 안 보이는 선의 곡률은 잴 수 없고, 억지로 재려 들면 장애물
자체의 윤곽을 곡률로 오인한다. 두 근거를 OR 로 합친다.

- **경로 기반**: `/path/global` 위 자차 전방 `curvature_lookahead_m`
  안의 최대 곡률. 측위(`map<-base_link` TF) + 전역경로 수신이 둘 다
  있어야 값이 나온다.
- **시야 기반**: 노란 중앙선(yellow) 의 꺾임(`trackBendDeg`). 이
  트리거 자체가 `yellow.found_count > 0` 을 전제로 하므로 항상 가려지지
  않은 쪽이고, 측위/전역경로 없이도 매 프레임 계산된다.

경로 기반이 유일한 근거였을 때, 측위가 아직 안 뜬 기동 초반이나 시뮬
재시작 직후에는 `curvatureAheadKappa()` 가 항상 -1(무근거)을 내 곡률
판정이 통째로 꺼졌다. 그러면 **직선 구간에서 장애물에 가려진 흰선에도
그냥 pan 이 걸렸다** — 장애물 판정 자체도 같은 측위에 의존하므로
`obstacleAheadOnSide()` 마저 false 를 내 막을 방법이 없었다. 시야 기반이
이 공백을 메운다.

### 시계 주의

/perception/obstacles 나이는 **node clock 이 아니라 지금 처리 중인 영상
프레임 스탬프** 기준으로 잰다. 영상과 obstacles 는 스탬프 출처가 같으므로
(시뮬은 Gazebo, 실기는 시스템 클록) `use_sim_time` 설정과 무관하게
성립한다.

> node clock 으로 재면 `use_sim_time=false` 인데 센서가 sim time 을 달고
> 오는 순간 나이가 1e9 초로 나와 **판정이 영영 죽는다.** 실제로 그렇게
> 만들었다가 잡았다. 같은 이유로 Holding 경과시간도 이 시계로 잰다.

## 10. 성능

### 이 노드는 FPS 병목이 아니다 (2026-08-24 실측)

먼저 이걸 못 박아 둔다. 라이브 실측, 구독자 없는 실주행 조건:

| 항목 | 실측 |
| ----------------------------------- | -------------- |
| 카메라 입력 `/camera/image_raw` | 14.66 Hz |
| 노드 처리율 `/kau_lane_detection/status` | **14.65 Hz** |
| 노드 CPU | 13.5% → 프레임당 **9.2 ms** (BEV 480×360 시절) |
| 노드 CPU | 22.3% → 프레임당 **14.8 ms** (BEV 640×480, 현재) |

**드롭이 0이다.** 9.2 ms 면 이론상 100 Hz 까지 소화하므로 여유가 87% 다.
640×480 으로 올린 뒤에도 14.8 ms → 67 Hz 로 여유가 78% 다.

느린 것은 **카메라 소스** 쪽이고, 같은 토픽을 부하 조건만 바꿔 재면
그대로 드러난다 — 노드를 **끈 상태에서도** 값이 같다:

| 조건 | `/camera/image_raw` |
| --------------------------- | ------------------- |
| 시스템 한가할 때 | 14.7 Hz |
| rviz2 + 전체 스택 | 8.0 Hz |

GPU 없는 개발 머신에서 `gz sim` 이 30 Hz 카메라를 CPU 로 래스터라이즈
하기 때문이다. 실측 상위 소비자:

| 프로세스 | %CPU (4코어 = 400%) |
| ----------------------------------- | ------------------- |
| `gz sim` (헤드리스 렌더링) | 107 |
| **`gz-launch` websocket 스레드 하나** | **86.5** |
| `webserver_node.py` | 44.2 |

**gzweb websocket 이 브라우저 클라이언트 수에 비례해 커진다.** 클라이언트가
없을 때는 2.7% 였다가, 포트 9002 에 연결 12개가 붙자 86.5% 가 됐다
(`websocket.gzlaunch`: `publication_hz 30`, `max_connections 10`).
3D 뷰 탭을 닫으면 코어 0.8개가 그대로 돌아온다.

**실차에는 이 항목들이 통째로 없다.** 다만 "실차는 30 Hz" 라고 적어 뒀던 것은
틀렸다 — 실차 카메라도 **15 Hz** 다:

```yaml
# physicar-ros/physicar_bringup/config/driver_params.yaml
camera:
  width: 640
  height: 480
  format: "BGR888"
  FrameDurationLimits: [66666, 66666]   # 66.666 ms = 15 fps
  undistort.out_width: 480              # 640x480 캡처 -> undistort -> 480x360 발행
  undistort.out_height: 360
```

즉 실차로 옮겨도 이 노드의 프레임 부하는 시뮬(14.7 Hz)과 같다. 늘어나는 것은
프레임 수가 아니라 **코어당 성능이 낮아지는 쪽**이다 (Pi 5 Cortex-A76 2.4 GHz).

★ 그리고 **왜곡보정이 두 번 돈다.** 위 설정대로면 카메라 드라이버가 이미
`cv::remap` 으로 왜곡을 편 480x360 을 `/camera/image_raw` 로 낸다
(`undistort.k1 -0.3675 ... dist_scale 0.7`). 그런데 이 노드는
`/camera/camera_info` 의 D 로 또 한 번 remap 한다. `camera_info_url` 이
physicar_bringup 어디에도 설정돼 있지 않아 `cim.getCameraInfo()` 가 무엇을
내는지 실차에서 확인해야 한다:

  ros2 topic echo --once /camera/camera_info

  D 가 전부 0    -> 기하는 맞고 프레임당 remap 한 번이 순수 낭비다
  D 가 0 이 아님 -> **이중 보정이라 BEV 기하가 틀어진다** (소실점부터 어긋남)

### 적용한 최적화 (실측)

| 항목 | 효과 |
| ------------------------------------- | ------------------------------- |
| 슬라이딩 윈도우 밀착 bbox | 1.672 → 0.889 ms/frame (1.9배) |
| `debug_image` 지연 생성 | 0.54 ms/frame (14.3% → 13.5%) |
| `cv::setNumThreads(1)` | 처리량이 아니라 **제어 지터** 목적 |
| `undistort` 맵 캐싱 | `initUndistortRectifyMap` 1회 + `remap` 반복 |
| CMake `Release` 기본값 | clean build 시 `-O0` 로 떨어지는 것 방지 |

**밀착 bbox** — 창을 `hypot(half, margin)` 반경의 정사각형으로 훑고 있었다.
직진(θ=−π/2)에서 84×84 = 7056 px 를 훑는데 실제 창은 80×25 = 2000 px 뿐이라
3.5배를 헛돌았다. 회전 사각형의 밀착 bbox 로 바꿨다:

```
ext_x = half·|cosθ| + margin·|sinθ|
ext_y = half·|sinθ| + margin·|cosθ|
```

`dx = u·cosθ − v·sinθ` 이므로 창 안의 점은 반드시 이 박스 안이다 →
**결과가 비트 단위로 같다.** 벤치마크에서 두 방식의 누적합이 정확히
같은 값(`81233464.3`)으로 나와 실측으로도 확인했다.

**`cv::setNumThreads(1)`** — OpenCV 기본값은 코어 수만큼이라, `remap` /
`warpPerspective` / `cvtColor` / `inRange` / `morphologyEx` 를 부를 때마다
4코어짜리 Pi 5 의 전 코어를 순간 점유한다. 그 사이 제어 루프가 스케줄에서
밀려 주기가 흔들린다. 480×360 은 한 코어로도 충분히 작아 분할 이득보다
스레드 깨우는 비용이 크다. 벤치할 때만 `KAU_OPENCV_THREADS=4` 로 덮는다.

### 이미지 발행은 구독자가 있을 때만

`sensor_msgs/Image` 하나를 만드는 데 480×360 BGR8 기준 518 KB 복사 +
직렬화 + DDS 전송이 든다. 예전에는 그런 토픽을 **6개 무조건** 발행해
프레임당 약 2.4 MB, 14 Hz 면 **초당 34 MB** 를 아무도 안 볼 때도 만들었다.

지금은 `get_subscription_count() > 0` 일 때만 만든다.

발행만 막는 것으로는 부족했다. **정작 비싼 쪽이 그대로 남아 있었다** —
`bev_frame.clone()`(518 KB) + 창 테두리 `cv::line` 약 180회(창 45개 × 4변)
+ 추적선 폴리라인 + `putText` 4~5줄 + `drawPathOverlay` 를 아무도 안 볼 때도
매 프레임 돌렸다. `putText` 는 글리프를 매번 래스터라이즈하므로 특히 비싸다.
지금은 구독자가 없으면 `debug_image` 를 **만들지도 그리지도** 않는다 —
빈 `cv::Mat` 을 sentinel 로 써서 `detectLaneSlidingWindow` /
`drawPathOverlay` 가 `empty()` 를 보고 건너뛴다.

### 제거한 것

- **`hls_binary` / `combined_binary` 토픽** — 알고리즘이 쓰지 않고 웹 뷰어도
  구독하지 않았다. 게다가 **동일한 이미지를 두 토픽에 각각 만들어** 발행했다.
- **`combined_binary` 계산** — `bitwise_or` 가 형태학 연산 전후로 **두 번**
  호출됐고 첫 결과는 그대로 버려졌다.
- **Sobel / Edge** — 노랑+흰 마스크만 쓰므로 진작 빠져 있었다.

len=77.3 rad=6139.1 maxlat=0.3 cte=0.01 yaw=-0.13 coff=0.1 csrc=1

| 필드                     | 뜻                                                |
| ------------------------ | ------------------------------------------------- |
| `lw/yw/rw`               | 좌/노랑/우 실제로 픽셀을 잡은 스텝 수             |
| `path` / `gate`          | 경로 생성 여부 / 게이트 기각 코드 (0 = 통과)      |
| `cte` / `yaw`            | 중앙선 대비 횡오차 [cm] / 헤딩오차 [deg]          |
| `coff` / `csrc`          | 중앙선 대비 자차 횡거리와 그 근거                 |
| `pan` / `pdeg` / `padeg` / `pgdeg` | pan 상태 / 발행각 / 최신 실측각 / 목표각 |
| `pdfix` / `pdext`        | 영상 시각 보간으로 적용된 각도 보정 [deg] / 범위 밖 절단 여부 |
| `conf` / `edev`          | EMA 신뢰도 / 관측-추정치 편차 [cm]                |
| `egate` / `erej`         | **실제로 적용된** 이상치 게이트 [cm] (dt 로 넓힌 뒤) / 연속 기각 수 |
| `pbend` / `pvis`         | 꺾임각 [deg] (진단 전용) / 정면에서도 남는 점 수  |
| `paim` / `pav`           | 조준각 [deg] (§8-b) / 조준 성립 여부 (0 이면 탐색 상태기계로 대체 중) |

`edev > egate` 인 프레임이 기각된 프레임이다. 둘을 나란히 봐야 "왜 안
섞였는지" 가 설명된다 — `egate` 는 설정값(`path_ema_gate_cm`)이 아니라
그 프레임의 dt 로 넓혀진 값이다 (§7).

`lane_failure_logger.py` 가 이 문자열을 정규식으로 파싱한다 (`key=value`
꼴이면 필드를 추가해도 깨지지 않는다).

### 콘솔 로그 정책

**정상 인식 상태에서는 콘솔에 아무것도 찍지 않는다.** 매 프레임
상태를 알고 싶으면 위 토픽을 본다:

```sh
ros2 topic echo /kau_lane_detection/status
```

예전에는 1 Hz 로 `Sliding Window | L 15 | Y 14 | R 15 | path ...` 와
`quintic Bezier ctrl [cm] (...)` 두 줄이 계속 나갔다. 같은 정보가
status 토픽과 debug_image 오버레이에 이미 들어 있어 중복이었고,
그 소음에 묻혀 정작 봐야 할 이상 징후가 안 보였다. 그래서 지웠다.
(`status` / `path_text` 문자열 자체는 debug_image 오버레이가 쓰므로
남아 있다.)

콘솔에 남긴 것은 **비정상 상황뿐**이다:

| 부류      | 예                                                           |
| --------- | ------------------------------------------------------------ |
| 차선 오인 | 흰선이 노란선과 겹침, 좌/우가 같은 선을 뭄, 회랑 이탈, 맵 단면 불일치 |
| 경로 끊김 | 경로 기각, EMA 추정치 폐기/재잠금, cusp                      |
| pan       | 탐색 시작/성공/실패, 복귀 보류/가능, 장애물 억제             |
| 설정 오류 | intrinsic 무효, BEV 기하 모순, 축척 불일치, 주점-BEV 중심 어긋남 |
| 센서      | CameraInfo 미수신, LaserScan 노후                            |

기동 시 한 번 찍히는 요약(도로 단면, BEV src/dst, intrinsic, 축척,
차로 폭 유도)은 남겼다. 이 값들이 맞는지가 이후 모든 판정의 전제라
매번 확인할 값이지 소음이 아니다.

## 12. 알려진 미해결

- **`bev_out` 이 500×480 인데 §3 의 표는 640×480 기준이다.** yaml 주석에
  따르면 실차 화각이 104° → 85° 로 좁아져 캔버스 폭을 같은 비율로 줄인
  것(640 → 500)이고, 그래야 `sx`(0.1207) / 비등방(2.62) /
  `lane_width_px`(258.8) 가 보존된다. §3 의 실측표는 그 전 세대 값이므로
  숫자를 그대로 읽으면 안 된다.
- **`updatePanSearch` 821줄 / `buildCenterlinePath` 582줄이 아직 크다.**
  §14 의 모듈 분할로 9,661줄 단일 파일은 없어졌고 `imageCallback` 도
  단계 11개로 쪼갰지만, 이 둘은 한 함수 그대로다. `updatePanSearch` 는
  상태기계라 단계 분해가 어렵고, `buildCenterlinePath` 는 후보 3개 합성
  → 적합 → 승격 → 게이트가 한 몸이다.
- **주석 정리가 헤더에 남았다.** `node_setup.cpp` 는 정리했다 — 파라미터
  근거의 집은 `config/lane_detection.yaml`, 실측표의 집은 이 문서(§13)로
  옮기고 선언 옆에는 한 줄만 남겼다 (1,331 → 1,103줄). 반면
  `kau_lane_detection_node.hpp` 는 여전히 **53%(845줄)가 주석**이고
  내용 대부분이 이 문서 §2/§5/§6/§8 과 중복이다. 그중 §2 를 옮겨 적은
  대목은 이미 낡았다 (차로 폭을 아직 31.25 cm 로 적고 있다 — 확정값은
  31.7). 근거는 이 문서로 모으고 선언부에는 계약만 남길 것.
- **`kau_lane_detection_node.cpp` 의 `setNumThreads` 주석이 "480x360" 을
  근거로 든다.** 원본 프레임은 여전히 480×360 이지만 `warpPerspective`
  이후 파이프라인(HLS 변환 / `inRange` / 모폴로지 / 슬라이딩 윈도우)은
  이제 640×480 위에서 돈다. 1 스레드 결정 자체는 그대로 유효하나
  (목적이 처리량이 아니라 제어 지터다) 근거 문장은 갱신이 필요하다.
- **차선 검출에 edge 근거가 없다.** HLS `inRange` 두 번이 전부라,
  색만 맞으면 잔디·연석·정지선·젖은 아스팔트 반사가 마스크를 통과한다.
  지금은 하류 기하 게이트가 사후에 걷어내는 구조다 — "잘못 잡고 나서
  버리기". 마스크 단계에 Sobel 등 gradient 조건을 AND 로 걸어야
  근본이 잡힌다 (§4).
- **`path_frame_id` 는 현재 yaml 에서 `base_link` 다** (대회장 노이즈로
  절대측위를 신뢰할 수 없어서). 아래는 `map` 으로 되돌릴 때의 이야기다.
  **`path_frame_id: map` 은 측위가 떠 있어야 발행이 나간다.**
  Cartographer/AMCL 이 아직 안 뜬 상태(기동 초반, pure localization
  초기화 전)에는 `map <- base_link` TF 가 없어 `/lane/center` 가
  아예 안 나간다 — 예전에는 base_link 라 이 의존이 없었다. 측위 없이
  검증할 때는 `path_frame_id:=base_link` 로 켤 것 (§1).
- **`pan_pivot_offset_x_cm` / `_y_cm` 이 (0,0) 초안값이다.** pan 회전
  보정의 피벗을 base_link 원점으로 근사한 것이라, 크게 panning 한
  프레임에서는 실제 pan 축 위치(URDF 실측 약 (5,0)cm)와의 오차만큼
  경로가 옆으로 밀려 나온다. 피벗이 d 만큼 어긋나면 오차는
  `d·2sin(θ/2)` 이므로 θ=15° 에서 1.3 cm, 30° 에서 2.6 cm 다 —
  **각도별 고정 편향이지 프레임간 튐이 아니다.** 그래서 우선순위는
  낮지만 공짜로 고칠 수 있다. 카메라 마운트 재실측 시 같이 넣을 것 (§8).
- **pan 램프와 각도 시각 보정은 실제 pan 사이클로 아직 검증 못 했다.**
  관측 구간에서 pan 이 0회 돌았다. `pdfix` 가 pan 중에 얼마나 커지는지,
  램프가 "꺾다 말다" 를 재현하지 않는지 확인해야 한다 (§8).
- **EMA 재잠금 폐기 경로가 미구현이다.** `path_ema_reset_frames`(14) 는
  yaml 과 선언부에 있지만 **어디서도 쓰이지 않고**, `ema_miss_streak_`
  는 0 으로 초기화만 될 뿐 증가하는 곳이 없다. 즉 "관측이 오래 없으면
  추정치를 폐기한다" 는 동작은 문서에만 있다 (§7).
- **`isRegular` 실패 프레임이 그대로 발행된다.** `robustifyPath` 는
  degenerate 판정 시 경고만 내고, 코드 주석 자체가 *"path_ema_ctrl_ 를
  되돌리거나, 최소한 발행은 건너뛰는 처리 필요"* 라고 적고 있다.
  뒤틀린 제어점이 `path.ctrl` 로 그대로 나간다 (§7).
- **tilt 는 기동 시 한 번 세우는 고정 자세다.** 제어량이 아니다 —
  `camera_tilt_deg`(10.0, + = 아래)를 `camera_tilt_repeat_s` 동안 1 Hz 로
  `/camera/tilt` 에 발행하고 타이머를 끈다. `bev_vanishing_y` /
  `bev_src_top_y` / `bev_src_bottom_y` 가 이 각도를 전제하므로
  (`y = cy + fy·tan(atan(h/d) − alpha)`, `alpha = 틸트 + 0.284`)
  틸트를 바꾸면 셋을 반드시 같이 다시 유도할 것 (§0-1). **실차에서
  실제로 10도가 서는지, 지평선이 132.54 행에 오는지는 아직 검증 못
  했다.** pan 과 달리 되먹임이 없어 명령이 먹지 않아도
  (예: `camera_engaged()`) 노드는 모른다. 실차 주점은 시뮬보다 10.4 px
  위인데 §0-4 로 같은 값을 쓰기로 했으므로, 그 오차도 여기서 같이
  확인할 것.
- **`curve_ahead_kappa_thresh` / `curve_ahead_bend_deg_thresh` /
  `obstacle_ahead_max_m` 실측 전 초안값.** 1.5m 룩어헤드, 15deg 꺾임,
  1.0m 장애물 거리 다 아직 안 재고 잡았다 (§9).
- **EMA 자기운동 보정 없음.** TF 는 이제 있지만 EMA 는 아직 안 쓴다 (§7).
- **`use_sim_time: false`** 로 도는데 센서 스탬프는 sim time 이다. pan/라이다
  경로는 프레임 스탬프로 우회했지만, 다른 곳에서 node clock 을 쓰면 같은
  함정에 빠진다.

## 13. 코드에서 옮겨온 실측 근거

§2~§12 에 없던 값들이다. 원래 `declare_parameter` 옆 주석에 있었는데,
파라미터의 집은 `config/lane_detection.yaml` 이고 근거의 집은 이 문서라
여기로 모았다.

### BEV src 사다리꼴 — 윗변은 주지 않고 유도한다

```
top_width = bottom_width * (top_y - vanishing_y) / (bottom_y - vanishing_y)
```

이렇게 하면 `top_y` / `bottom_y` 를 바꿔도 BEV 에서 차선이 계속 평행하게
유지된다. `bev_test.png` 기준 차선 간격은 y=270 에서 434 px, y=320 에서
683 px(화면 밖)이라 **`bottom_y` 상한이 270 근처**다.

소실점은 live undistort 프레임을 직접 스윕해 179.0 에서 위/아래 간격이
일치했다 (위 194.9 / 아래 195.4). 예전 값 184.7 은 `bev_test.png` 를
역변환해 복원한 영상에서 뽑아 편향돼 있었다 — 그 값에서는 위쪽 간격이
234 px 로 아래(195 px)보다 20% 넓었다.

### bev_src_top_y — 검정 비율과 검출률의 교환

`margin 0.25`, `bottom_y 270` 에서 live 프레임 실측:

| `top_y` | 검정 % | 차선 간격 | look-ahead | 창검출 Y/L/R |
| ------- | ------ | --------- | ---------- | ------------ |
| 205 | 9.9 | 195 | 3.5x | 9/9 9/9 9/9 |
| **195** | **5.2** | **195** | **5.7x** | **9/9 9/9 9/9** |
| 191 | 3.7 | 196 | 7.6x | 7/9 9/9 9/9 |
| 185 | 1.7 | 197 | 15.2x | 5/9 8/9 7/9 |

차선 간격은 하단 스케일이 정하므로 `top_y` 와 무관하다. 더 내리면 검정은
줄지만 원거리가 과하게 늘어나 점선 노랑이 뭉개져 검출이 떨어진다.

### window_margin — 곡선 끊김의 지배적 원인이었다

창 높이가 360/9 = 40 px 이므로, 차선이 창 하나당 `margin` 보다 많이 옆으로
빠지면 그 창은 차선을 놓친다. 곡률(BEV 최상단 횡이동)별 창당 횡이동:

| 곡률 | 창당 횡이동 |
| ---- | ----------- |
| 100 px | 19.8 px |
| 140 px | 27.7 px ← margin 25 는 여기서 이미 실패 |
| 180 px | 35.6 px |
| 220 px | 43.5 px |

상한은 차선 간격(105 px)의 절반인 **52 px** 다. 그 이상이면 옆 차선을 창
안에 물어버린다. 합성 곡선 검증(곡률 260 px, 3차선 평균 창검출률):
margin 25 → 70%, margin 40 → 89%.

### histogram_band_ratio — 전체 표

§5 의 표는 두 줄만 실었다. 전체는 이렇다 (실패 70장, peak 오차):

| 밴드 | 중앙 | 90%ile | 최대 | margin 초과 | 차로폭 초과 |
| ---- | ---- | ------ | ---- | ----------- | ----------- |
| 0.40 | 14 | 157 | 325 | 21장 | 9장 |
| 0.20 | 9 | 53 | 260 | 11장 | 1장 |
| **0.10** | **4** | **34** | **65** | **4장** | **0장** |

**"차로폭 초과" 는 아예 다른 차선을 잡았다는 뜻이다.** 이때도 슬라이딩
윈도우는 무언가를 따라가며 9/9 을 보고하므로 창 수만 보면 드러나지 않는다.
자신 있게 틀리는 실패다.

### 발행 게이트가 왜 필요했나

맵 1바퀴(1546 프레임) 실측에서 **근거가 한쪽 차선 3창뿐인데도 곡률반경
45 cm 경로를 발행했다.** 휠베이스 18 cm / 최대조향 20° 면 최소 회전반경이
49.5 cm 라, 물리적으로 불가능한 명령이 컨트롤러로 나간 것이다.

원인은 자유도다 — **창 3개로 2차 적합하면 자유도 0, 잔차 0 인 완전
결정계**라 아무리 엉터리여도 "완벽하게 맞는" 곡선이 나온다. 잔차로는
절대 걸러지지 않는다.

## 14. 파일 구성

한 클래스의 구현을 역할별 TU 로 나눠 담는다. 헤더는
`kau_lane_detection_node.hpp` 하나이고, 자료형과 상태 없는 기하만
별도 헤더로 뺐다.

| 파일 | 역할 |
| ---- | ---- |
| `lane_types.hpp` | 단계 사이를 오가는 자료형 (`LaneDetectionResult` / `LanePath` / `CenterFix` / `FrameContext` …) |
| `lane_geometry.hpp/.cpp` | 상태 없는 기하. 폴리라인 횡거리, 가중 다항 적합, 방향 판정 (`kau_lane::geom`) |
| `bezier.hpp` | quintic Bezier 연산 (호길이/곡률/최근접점/분할) |
| `road_map.hpp` | 도로 **단면의 형태**. 크기는 yaml 이 정한다 (§0-3) |
| `node_setup.cpp` | 생성자 — 파라미터 선언, 퍼블리셔/서브스크립션 배선 |
| `bev_geometry.cpp` | BEV 사다리꼴, 축척(cm/px), CameraInfo |
| `camera_pose.cpp` | pan 각 이력/램프 발행, tilt 고정 자세 |
| `lane_detect.cpp` | 히스토그램 시작점 + 방향성 슬라이딩 윈도우 |
| `center_resolve.cpp` | 단면 판정(`identifyLine`), 중앙선 대비 자차 횡거리 |
| `path_build.cpp` | 제어점 생성, EMA 강건화, 발행 게이트 |
| `path_publish.cpp` | `KauPath` / RViz 이산화 발행 |
| `pan_aim.cpp` | 조준각 (§8-b) — 전역경로 근거와 차선 근거 |
| `pan_search.cpp` | 소실 탐색 상태기계 (§8, 조준 fallback) |
| `map_context.cpp` | 측위 TF, 전역경로 곡률, 장애물 판정 (§9) |
| `debug_view.cpp` | 오버레이 렌더링 |
| `lane_pipeline.cpp` | 프레임 파이프라인 — `imageCallback` 이 단계를 순서대로 부른다 |

### 파이프라인 단계

`imageCallback` 은 순서만 정하고, 단계끼리는 **`FrameContext` 로만**
이어진다. 단계 함수는 서로를 모른다.

```
stagePrepareFrame     1-2  ROS Image -> undistort   (false 면 프레임 폐기)
stageBuildBev          3   BEV 원근변환 + 파라미터 재독
stageBuildMasks       4-7  HLS -> 노랑/흰 마스크 -> 형태학
stagePrepareDebugCanvas 8  디버그 캔버스 (구독자 없으면 안 만든다)
stageDetectLanes     12-16 히스토그램 + 세 차선 슬라이딩 윈도우
stageValidateSides   16-a  좌/우 검증 + 회랑 절단
stageResolveCenter   16-b  중앙선 대비 자차 횡거리
stageRestoreMissing  16-c  한쪽 흰선 소실 복원
stageBuildPath       16-d  Bezier 생성 -> EMA -> pan 조준
stagePublishPath     16-e  경로 발행
stageRender         17-21  오버레이 / status
```

절 번호(1, 3, 16-a …)는 예전 단일 `imageCallback` 의 섹션 번호를 그대로
쓴다. 로그와 이 문서의 다른 절이 그 번호를 참조하기 때문이다.
